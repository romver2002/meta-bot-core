# ADR-0013: Структурное логирование и файлы ошибок

## Контекст

Спека наблюдаемости ([../ops/observability.md](../ops/observability.md))
написана давно и подробна (уровни, обязательные точки, запреты на секреты/ПДн,
`request_id`), но помечена «уточнить у команды» и **кодом не реализована**:
`logging` встречается в одном файле (фоновая чистка BR-008), настройки нет,
необработанные исключения летят голым текстом uvicorn, best-effort-подавления
(ack, notify) молчат. Владелец просит «по-современному» и «файлы, где можно
посмотреть ошибки».

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| 1. Оставить как есть | ничего не делать | инциденты неразбираемы; спека мертва |
| 2. structlog | богатый DX, bind-контексты | новая зависимость (tech-stack: добавления обосновываются), та же JSON-цель достижима stdlib'ом |
| 3. loguru | простой API | глобальный синглтон-стиль, чужой для stdlib-экосистемы (uvicorn/alembic) |
| 4. stdlib `logging` + свой JSON-форматтер + `ContextVar` | ноль зависимостей; родная интеграция со всем стеком; форматтер ~30 строк | чуть больше своего кода |
| Файлы: писать логи приложением всегда | «файлы ошибок» из коробки | 12-factor нарушен: в проде лог-файлы внутри контейнера теряются и не агрегируются |
| Файлы: только stdout + Docker-драйвер | канонично | локально на Windows файлы неудобны владельцу |

## Решение

Вариант 4 + компромисс по файлам:

- **Формат**: каждая запись — одна JSON-строка (`ts` ISO-8601 UTC, `level`,
  `logger`, `message`, `request_id`, доп. поля через `extra`, `exc_info` текстом).
  Библиотека — stdlib `logging` (прямая сборка handlers в `configure_logging`), без новых зависимостей.
- **Корреляция**: `request_id` живёт в `ContextVar` в **application**-слое
  (`application/observability.py`) — его могут импортировать и presentation
  (middleware ставит из `X-Request-ID` или генерирует), и infrastructure
  (его читает `JsonFormatter`). Ответ всегда несёт `X-Request-ID`.
- **Куда пишем**: всегда **stdout** (12-factor; в проде подберёт агрегатор).
  Дополнительно, если задан `LOG_DIR`, — ротируемые файлы `app.log` (всё) и
  `errors.log` (ERROR+): это ответ на «файлы с ошибками» для локальной
  разработки; в compose каталог смонтирован на хост (`./logs`). В проде
  `LOG_DIR` не задаётся.
- **Границы CA**: настройка — composition root (`main.py` вызывает
  `infrastructure/observability/logging_setup.configure_logging`); middleware и
  500-handler — presentation; сами логгеры — stdlib в любом слое (домен не
  логирует — он чистый).
- **Точки** (по спеке observability.md): HTTP-доступ (метод, путь, статус,
  длительность, `request_id`), необработанное исключение → ERROR со стеком +
  ответ 500 с `request_id`; вебхук — принят/дубль/`processed=false`;
  best-effort-подавления движка (ack, notify) — WARN вместо молчания.
  Секреты/ПДн не пишем: тексты/`payload` — только DEBUG (спека, раздел
  «Логировать запрещено»).

Дополнительно: болтливые сторонние логгеры (`httpx`/`httpcore`) принудительно
на WARNING (httpx печатает полный URL — у Telegram в нём токен), а форматтер
вычищает `/bot<token>/` из message/exc_info/stack любой записи (защита в глубину).

Вне решения (следующие этапы): Sentry/exception-tracker, метрики
Prometheus, латентность Bot API в адаптерах, трейсы OpenTelemetry.

## Последствия

**Положительные:**
- Инцидент разбираем: `errors.log`/stdout со стеком и `request_id`, путь
  запроса прослеживается насквозь.
- Молчаливые best-effort-подавления становятся видимыми (WARN).
- Ноль новых зависимостей.

**Отрицательные:**
- Свой форматтер — ~80 строк кода на поддержке.
- Логи uvicorn (access) остаются в его формате до отдельной интеграции.

**Риски:**
- Утечка ПДн/секретов в `extra` — контролируем правилами спеки и ревью;
  тексты пользователей в логах только на DEBUG.
- Рост файлов при включённом `LOG_DIR` — ротация 5 МБ × 5 файлов.
