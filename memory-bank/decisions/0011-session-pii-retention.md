# ADR-0011: Ретеншен и стирание ПДн сессий (BR-008)

## Контекст

`Session.variables` хранит ответы пользователей (имя, контакт — ПДн) durable
в PostgreSQL JSONB **бессрочно и открытым текстом**; `external_user_id`/
`external_chat_id` — тоже ПДн. Аудит зафиксировал расхождение: считалось
«эфемерно в Redis», по факту — вечное хранение. Обращение с ПДн (152-ФЗ)
требует цель, ограниченный срок и согласие; бессрочное накопление контактов
всех пользователей — и юридический, и security-риск (radius утечки БД).

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| 1. Оставить как есть | ничего не делать | нарушение принципов обращения с ПДн; растущий radius утечки |
| 2. Шифровать variables в БД | защита при утечке дампа | не решает бессрочность и согласие; ключи — тот же нерешённый vault |
| 3. Не персистить variables вовсе (только Redis+TTL) | минимум ПДн | ломает ADR-0008 (восстановление FSM после рестарта), заявка теряется при сбое |
| 4. Минимизация + ретеншен + согласие | срок жизни ПДн = потребность; совместимо с ADR-0008 | фоновая задача и политика срока |

## Решение

Вариант 4, три уровня (**BR-008**):

1. **Домен**: `Session.complete()`/`expire()` стирают `variables` — данные
   сценария живут не дольше сессии (к завершению все сайд-эффекты выполнены).
2. **Фоновая чистка** (`PurgeExpiredSessionsUseCase` за новым портом
   `SessionRetentionPort`, ISP — движку он не нужен): (а) активные сессии без
   событий дольше `SESSION_IDLE_TTL` → expired + стирание переменных (заодно
   освобождает зависший FSM); (б) завершённые/просроченные старше
   `SESSION_RETENTION_DAYS` → строка удаляется целиком, включая
   `external_user_id`/`external_chat_id`. Запуск — задача в lifespan
   composition root каждые `SESSION_PURGE_INTERVAL` секунд; `now` передаётся
   в use case параметром (часов в application-слое нет).
3. **Согласие — данные Flow**: сбор ПДн в сценарии начинается только после
   явного «Согласен» (экран согласия); в примере first-bot — гейты перед
   формой заявки и связью с разработчиком. Ядро про согласие не знает —
   это конструкция сценария (конструктор, не один бот).

Границы и смежные каналы:
- `publish_audit` — ПДн нет по конструкции; доставленные уведомления в чатах
  платформ — вне нашего хранения (стирание чатов нам не подконтрольно).
- **Свободный текст AI-вопроса** (`user_question`) хранится в `variables`
  (тот же ретеншен) и **передаётся внешнему AI-провайдеру** (OpenRouter) —
  сценарий обязан уведомлять об этом до ввода (в примере first-bot — прямо
  в prompt) и не поощрять ввод ПДн.
- Ключи идемпотентности Redis не содержат ПДн: составные ключи MAX хэшируются
  (sha256) в адаптере; TTL — `WEBHOOK_IDEMPOTENCY_TTL`.
- Отмена/доставка заявки в примере стирает переменные немедленно
  (save-узлы-стиратели) — не дожидаясь idle-TTL.

## Последствия

**Положительные:**
- ПДн живут ровно столько, сколько нужны; radius утечки ограничен сроком.
- Зависшие FSM освобождаются — «залипшая» сессия не держит пару (Bot, user) вечно.

**Отрицательные:**
- Диалог, брошенный дольше idle-TTL, начинается заново (переменные стёрты).
- Ещё одна фоновая задача в процессе API (до выделенного планировщика).

**Риски:**
- Один процесс = одна чистка; при горизонтальном масштабировании нужны
  advisory-lock/выделенный воркер — пересмотреть при переходе к нескольким репликам.
- Слишком агрессивный idle-TTL ломает долгие диалоги — значение конфигурируемо,
  наблюдать по жалобам «бот забыл разговор».
- Просрочка применяется фоновым проходом, а не при чтении: между idle-TTL и
  проходом `get_active` ещё вернёт «протухший» диалог; окно ≤ интервала чистки.
- Гонка purge с in-flight обработкой update может пересохранить только что
  просроченную сессию — окно мало, следующий проход дочистит.
