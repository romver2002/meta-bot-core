# ADR-0001: Clean Architecture + SOLID, строгий режим

## Контекст

meta-bot-core — конструктор сценариев чат-ботов и mini app для нескольких
платформ (Telegram, MAX, в перспективе VK/WhatsApp). Главный риск такого продукта —
превращение в «кашу из `if telegram`, `if max`»: разные форматы callback, разные
кнопки, разные mini app SDK, разные правила публикации. Действующие силы:

- **Много платформ, одно ядро.** Сценарии, состояния, тексты, каталог, заказы не
  должны зависеть от мессенджера. Если платформенные различия протекут в ядро,
  добавление каждой новой платформы будет переписывать логику.
- **AI-driven разработка.** Значительную часть кода пишут агенты (Claude Code,
  Codex). Агенту нужна предсказуемая структура и **машинно-проверяемые** границы,
  иначе он воспроизводит и усиливает протечки.
- **Пользовательский код в сценариях.** Python-блоки конструктора должны исполняться
  изолированно; ядро нельзя оставлять открытым для прямых вызовов из них.
- **Тестируемость.** Логику сценариев нужно проверять юнит-тестами без поднятия БД,
  Redis и обращения к Telegram/MAX.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| 1. Оставить «как проще» (логика вперемешку с SDK платформ) | Быстрый старт | `if platform` расползается по коду; вторая платформа удваивает стоимость; тесты требуют сети |
| 2. Слоистая архитектура (UI → Service → DAO) | Знакома, дешевле внедрить | Зависимости вниз к БД/SDK: домен зависит от инфраструктуры; границы не проверяемы |
| 3. Clean Architecture + SOLID, **границы декларативны** | Домен изолирован | «CA на бумаге»: без автопроверки границы медленно разъезжаются |
| 4. Clean Architecture + SOLID, **строгий режим** (границы проверяет import-linter, протечка = красная сборка) | Домен изолирован и тестируем; направление зависимостей — единое проверяемое правило; предсказуемо для людей и агентов | Больше обвязки (порты, DTO, мапперы); порог входа; дисциплина на ревью |

## Решение

Принимаем **Clean Architecture + SOLID в строгом режиме**.

- Четыре слоя: `domain`, `application`, `infrastructure`, `presentation`; зависимости
  направлены только внутрь, к домену. Ответственность слоёв и дерево —
  [../architecture/overview.md](../architecture/overview.md).
- Домен не импортирует ничего из внешних слоёв и фреймворков; выход наружу — только
  через порты (`Protocol` в `application/ports/`), реализуемые в `infrastructure`.
- **Границы проверяются машиной**: import-linter (контракт `.importlinter`),
  команда `lint-imports` в pre-commit и CI-джобе `arch-lint`. Протечка слоя ломает
  сборку; правится разворотом зависимости, а не игнор-строкой (протокол —
  [../../.claude/rules/clean-architecture.md](../../.claude/rules/clean-architecture.md)).
- Отступления от границ — только через новый ADR.

## Последствия

**Положительные:**
- Ядро конструктора не знает о Telegram/MAX; новая платформа — это адаптер, а не
  правка логики (развитие темы — [0002-domain-core-and-adapters.md](0002-domain-core-and-adapters.md)).
- Домен и сценарии тестируются без БД/сети ([../architecture/testing-strategy.md](../architecture/testing-strategy.md)).
- Предсказуемая структура для людей и агентов; границы не разъезжаются молча.

**Отрицательные:**
- Больше кода-обвязки: порты, DTO, мапперы между слоями и платформами.
- Порог входа для разработчиков без опыта CA.

**Риски:**
- «CA на бумаге». Митигация — строгий режим: `lint-imports` в CI, красный линтер
  закрывает мерж.
- Переусложнение утилит вне ядра. Митигация: для мелких вспомогательных сервисов
  допустима упрощённая структура — фиксируется отдельным ADR.
