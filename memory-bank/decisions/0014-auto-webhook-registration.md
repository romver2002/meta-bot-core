# ADR-0014: Автоматическая регистрация вебхука при публикации

## Контекст

«Выгрузка бота на платформу» была наполовину ручной: `publish` проверял токен
и замораживал версию сценария, но URL приёма обновлений
(`/webhooks/{platform}/{bot_id}`) владелец регистрировал у платформы сам —
curl `setWebhook` для Telegram, `POST /subscriptions` для MAX
(examples/first-bot-request-assistant/README.md). Для пользователя-нетехнаря
это выглядит как «опубликовал, а бот молчит»; при смене домена все боты
пришлось бы перерегистрировать руками. Портируемый контракт был спроектирован
заранее: `register_webhook(url, secret)` → TG `setWebhook` / MAX
`POST /subscriptions` (specs/002-platform-deep-dive, «Установка webhook»).

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| 1. Оставить ручную регистрацию | ничего не делать | онбординг требует curl и знания API платформ; смена домена = ручная перерегистрация всех ботов |
| 2. Отдельный эндпоинт `POST /bots/{id}/webhook` | явный контроль | ещё один обязательный шаг онбординга — та же проблема «опубликовал, а бот молчит» |
| 3. Регистрация внутри `publish` (opt-in по `WEBHOOK_BASE_URL`) | публикация = бот работает; dev без туннеля не ломается (без переменной шаг пропускается); смена домена = смена env + повторный publish | сбой регистрации после успешной публикации требует внятной ошибки (решено: 502 с текстом «повторите публикацию», ретрай идемпотентен) |

## Решение

Вариант 3:

- **Порт**: `BotPlatformPort.register_webhook(RegisterWebhookCommand)` —
  `bot_token`, `url`, `secret`; идемпотентно (TG перезаписывает подписку,
  у MAX ключ подписки — сам `url`). Реализации: TG `POST setWebhook`
  (`secret_token` в теле, ошибки скрабятся от токена), MAX
  `POST /subscriptions` (токен в `Authorization`, ответ `SimpleQueryResult`).
  `allowed_updates`/`update_types` не сужаем: неподдерживаемые типы
  `parse_update` игнорирует, а список пришлось бы синхронизировать с движком.
- **Оркестрация**: шаг 6 `PublishBotUseCase` — после закрепления версии
  и сохранения бота. Сбой регистрации НЕ откатывает публикацию: use case
  оборачивает ошибку в `ApplicationError` с текстом «бот опубликован, но вебхук
  не зарегистрирован — повторите публикацию» (роут отдаёт 502); повторный
  `publish` идемпотентен по `content_hash` и повторяет только регистрацию.
- **Конфигурация**: `WEBHOOK_BASE_URL` (реализована планировавшаяся переменная,
  ops/configuration.md). Не задана — поведение прежнее, регистрация ручная
  (локальная разработка без постоянного туннеля). Форму пути
  `/webhooks/{platform}/{bot_id}` знает только composition root (он же
  монтирует роут) — application получает готовый шаблон.
- **Секрет**: используется существующий глобальный `WEBHOOK_SECRET`.
  Секрет per-bot (Telegram выдаёт `secret_token` на подписку) — известное
  улучшение мультитенантности, отдельным этапом вместе с IAM.

## Последствия

- Онбординг бота сокращается до: создать бота → сценарий → `publish`
  (шаг curl `setWebhook` из инструкций уходит).
- Смена публичного домена = смена `WEBHOOK_BASE_URL` + повторная публикация
  ботов (идемпотентная); массовая перерегистрация одним действием — кандидат
  в admin-инструменты позже.
- `unregister_webhook` (TG `deleteWebhook` / MAX `DELETE /subscriptions`)
  сознательно отложен до появления сценария «пауза/удаление бота» в API.
- Тесты: контрактные MockTransport-тесты обоих адаптеров
  (tests/unit/platforms/test_register_webhook.py) + оркестрация в
  tests/unit/application/test_publish_bot.py.
