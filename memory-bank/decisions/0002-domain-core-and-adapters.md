# ADR-0002: Доменное ядро + платформенные адаптеры (не «универсальный бот»)

## Контекст

Продукт можно понять двумя способами:

1. «Один бот, который одинаково работает в Telegram и MAX» — общий транспорт.
2. «Одно доменное ядро сценариев + разные адаптеры под платформы» — общий смысл,
   разная инфраструктура.

Первый способ ложный: у Telegram и MAX разные запуск, авторизация, кнопки, шаринг,
mini app bridge, правила публикации. Даже mini app — это не «одинаковый фронт в
разных мессенджерах», а общий web-продукт с разными platform bridge. Если это
различие протекает в ядро, получаем «кашу из `if telegram`/`if max`».

Важно и то, что конструктор **не создаёт платформенного бота**: аккаунт, модерация
и лимиты (в MAX — 5 ботов для организации/ИП, 2 для самозанятого) живут на стороне
платформы. Конструктор создаёт **поведение** уже зарегистрированного бота и
связывается с ним по токену (см. [../domain/business-rules.md](../domain/business-rules.md), BR-001–BR-003).

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| 1. Универсальный бот с ветвлением по платформе внутри логики | Меньше абстракций на старте | `if platform` в ядре; вторая платформа переписывает логику; невозможно тестировать без сети |
| 2. Отдельные кодовые базы под Telegram и MAX | Простая ментальная модель на платформу | Дублирование сценариев, состояний, каталога, CRM; расхождение поведения |
| 3. **Доменное ядро + платформенные адаптеры-плагины** | Ядро одно и платформонезависимо; платформа — плагин за портом; новая платформа не трогает ядро | Нужны порты, мапперы, capability matrix; больше обвязки |

## Решение

Строим продукт по формуле:
**Bot Constructor = Flow Engine + State Machine + Platform Adapters + Mini App Runtime.**

- Бизнес-логика оперирует абстракциями: сообщение, пользователь, кнопка, событие,
  сценарий (`Flow`), шаг (`Node`), состояние (`Session`), mini app, callback, файл.
  Термины — [../domain/glossary.md](../domain/glossary.md).
- Платформы (`Telegram`, `MAX`, далее `VK`, `WhatsApp`) — **плагины-адаптеры** в
  `infrastructure/platforms/*`, реализующие порт `BotPlatformPort`. Выбор платформы
  делает `PlatformFactory`; ядро вызывает `platform.send_message(command)` и не знает,
  во что это превратится ([../architecture/patterns.md](../architecture/patterns.md)).
- Входящие события платформ приводятся адаптером к единой модели `IncomingEvent`;
  дальше приложение работает только с ней.
- Общее (сценарии, состояния, тексты, каталог, заказы, CRM, webhook-pipeline) живёт
  в ядре; платформенное (парсинг update, формат кнопок, mini app bridge, авторизация,
  лимиты медиа, публикация) — в адаптерах.

## Последствия

**Положительные:**
- Новая платформа = новый адаптер + строка в capability matrix, без правки ядра.
- Ядро тестируется без Telegram/MAX; поведение единообразно между платформами.
- Различия платформ локализованы и обозримы.

**Отрицательные:**
- Порты, мапперы, единая модель события и capability matrix — дополнительный код.
- Соблазн «срезать угол» через `if platform` в ядре; пресекается ревью и
  арх-линтером (BR-005).

**Риски:**
- Абстракция «сообщение/кнопка» может не покрыть платформенную специфику. Митигация:
  специфичное отдаётся через capability matrix и platform-specific блоки
  ([0005-capability-matrix.md](0005-capability-matrix.md)), а не протечкой в ядро.
