# ADR-0010: Блок `notify` и адресаты уведомлений (NotificationTarget)

## Контекст

Сценарию нужно доставлять сообщение **третьему лицу** — не автору события:
форма заявки уведомляет админа, «связаться с разработчиком» — разработчика.
Движок сегодня шлёт только в чат текущего пользователя (`send()` в
`ProcessUpdateUseCase` жёстко адресует `event.external_chat_id`), поэтому
в первом боте доставка — заглушка «принято». При этом порт уже готов:
`SendMessageCommand` несёт произвольный `external_chat_id`.

Силы: конструктор, а не один бот — механизм обязан быть generic (любой
`chat_id`, любая роль); `chat_id` получателя — конфигурация бота и
потенциальные ПДн, ему не место ни в Flow-JSON, ни в базе знаний; доставка
может падать (получатель заблокировал бота) — сбой не должен рвать
user-facing ответ; ветвления по платформе в ядре запрещены (BR-005).

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| 1. Оставить как есть (заглушка) | ничего не делать | заявки не доставляются — головной сценарий не завершён |
| 2. `http_request` на `api.telegram.org/...sendMessage` | нет нового кода | протечка платформы в данные сценария (BR-005); bot-token утекает из vault в Flow/логи (запрет security.md); дублирует `BotPlatformPort.send_message` |
| 3. `chat_id` литералом в params блока | просто | ПДн в Flow-JSON/версиях/экспорте; смена адресата = переопубликация (BR-001) |
| 4. Блок `notify(to=роль)` + резолвер «роль → chat_id» за портом | generic; ПДн вне Flow; смена адресата без переопубликации; ноль платформенного в ядре | новый порт + блок + API |

## Решение

Вариант 4. Новый тип узла **`notify`** (`params`: `to` — символическая роль,
`text` — шаблон с переменными сценария). Движок резолвит роль в `chat_id`
через новый порт **`NotificationTargetResolverPort.resolve(bot_id, role)`**
(application/ports, контракт ошибок — только `ApplicationError`) и шлёт через
существующий `BotPlatformPort.send_message` — различия платформ остаются в
адаптерах. Пользовательские значения переменных при рендере текста уведомления
нейтрализуются (переводы строк → видимый «⏎», Cc/Cf-символы удаляются) —
ввод пользователя не может дорисовать «поля» карточки (антиспуфинг).

Границы: доставка **best-effort** — сбой (`ApplicationError`) и
неразрешённая роль не прерывают цепочку, исход узла всегда `next`
(гарантированная доставка — outbox/dead-letter — вне этого ADR, отдельным
этапом). Привязка «роль → chat_id» — конфигурация бота: dev-реализация
`FileNotificationTargets` (`.secrets/`, как token vault/connection secrets),
задаётся `PUT /api/bots/{bot_id}/notifications/{role}`; прод-хранилище — тот
же открытый вопрос, что и vault. Онбординг-захват `chat_id` командой в чате
(`/register_admin`) — следующий этап; сейчас админ узнаёт свой `chat_id` и
задаёт его через API.

## Последствия

**Положительные:**
- Заявка/вопрос реально доставляются человеку; сценарий первого бота завершён.
- Роли в Flow символические — Flow остаётся переносимыми данными без ПДн.
- Тот же блок покрывает любые нотификации любого бота (generic).

**Отрицательные:**
- Ещё один dev-файл в `.secrets/` до решения по прод-хранилищу секретов.
- Best-effort: потерянное уведомление незаметно для пользователя.

**Риски:**
- Молчаливая потеря уведомлений при постоянном сбое доставки — заметим по
  жалобам «заявки не приходят»; сигнал к внедрению outbox + метрики доставки.
- Роль без привязки в новом боте — уведомление тихо пропускается; смягчение:
  предупреждение при публикации (проверка привязок ролей) — кандидат в BR.
- Эндпоинт привязки живёт на неаутентифицированной поверхности Admin API
  (известная проблема IAM) — до IAM контур строго dev-only; формат role/chat_id
  валидируется на входе.
- Повторное нажатие «Подтвердить» по протухшей карточке доставляет карточку
  повторно (осознанно: ретраи платформы гасятся идемпотентностью update_id,
  а повторный явный клик трактуем как намеренную переотправку); дедуп
  уведомлений — вместе с outbox.
