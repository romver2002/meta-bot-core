# ADR-0007: Визуальный редактор сценариев — стек и границы (React + React Flow)

> Черновик на ратификацию командой. `accepted` ставит владелец раздела.

## Контекст

Конструктор — это визуальный редактор сценариев (Admin UI), где автор бота (в 80–90%
случаев не программист) собирает `Flow` мышью: перетаскивает блоки, соединяет их,
настраивает параметры. В базе знаний детально описаны домен и backend, а **сам
редактор-фронтенд по сути greenfield** — под него не было ни стека, ни ADR, ни кода.
Без этого решения нельзя начинать MVP Admin UI ([../product/roadmap.md](../product/roadmap.md)).

Силы, которые действуют:
- Нужен **отзывчивый** node-editor: панорама, зум, drag-and-drop узлов, «резиновые»
  связи, мини-карта. Требование пользователя — «быстро и чётко».
- Редактор **не должен** знать про платформы и **не генерирует код**: он редактирует
  `Flow` как **данные** (агрегат), которые в рантайме интерпретирует Flow Engine
  ([0003-flow-engine-blocks-and-sandbox.md](0003-flow-engine-blocks-and-sandbox.md)).
- Различия платформ во фронте — только **данные** CapabilityMatrix с backend, без
  `if platform ==` ([0005-capability-matrix.md](0005-capability-matrix.md), BR-005/BR-006).

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| 1. Оставить как есть (нет решения по фронту) | — | Блокирует MVP Admin UI; каждый начинает по-своему |
| 2. Свой холст с нуля (canvas/SVG) | Полный контроль над рендером | Дорого; высок риск тормозов; месяцы на «физику холста» |
| 3. **React + React Flow (`@xyflow/react`)** | Зрелый движок node-editor'ов; плавный холст из коробки; силы уходят на домен, а не на канвас; лицензия MIT (пермиссивная) | Зависимость от сторонней библиотеки; следить за версией/API |
| 4. Готовый no-code-конструктор общего назначения (встроить сторонний) | Быстрый старт «вширь» | Не ложится на доменную модель (Node/Trigger/Session-FSM); чужая модель данных |

## Решение

- Визуальный редактор — **отдельный фронтенд-продукт** (не часть backend), стек
  **React 18 + Vite + React Flow (`@xyflow/react`)**. Расположение — `frontend/constructor/`
  (рядом с будущим `frontend/mini-app/`, по аналогии с моделью «отдельный web-продукт»
  из [0006-mini-app-as-web-product.md](0006-mini-app-as-web-product.md)).
- Редактор редактирует `Flow` как **данные**: узел на холсте = `{ type, params }`,
  ребро = переход. Сериализует граф в агрегат `Flow` и обменивается им с backend через
  **Admin API**. **Никакой генерации кода** и **никакой платформенной логики** во фронте.
- Каталог узлов фронта — проекция [../domain/flow-blocks.md](../domain/flow-blocks.md)
  (4 триггера + 8 блоков, включая `custom_code` с пометкой песочницы, BR-004). Палитра
  приглушает недоступные на платформе блоки по CapabilityMatrix (BR-006).
- **Граница решения:** редактор **НЕ исполняет** `Flow` (это делает Flow Engine),
  **НЕ** обращается к платформам напрямую и **НЕ** хранит секреты. Всё платформенное
  остаётся за backend/адаптерами.

Статус — `proposed`. При ратификации: внести фронтенд-стек в
[../architecture/tech-stack.md](../architecture/tech-stack.md) (React/Vite/React Flow —
пермиссивная MIT, допустима правилом стека) и описать контракт Admin API.

## Последствия

**Положительные:**
- Отзывчивый холст без собственной «физики»; фокус разработки — на доменных блоках,
  панелях настройки и валидации.
- Единая модель «Flow как данные» тянет новые платформы без переписывания редактора.

**Отрицательные:**
- Зависимость от `@xyflow/react` (версию фиксируем; следим за миграциями API).
- Отдельный деплой-контур фронта (как и у mini app).

**Риски:**
- Редактор может начать «знать» про платформы (протечка платформенной логики во фронт).
  Митигация: различия — только данными CapabilityMatrix с backend; ревью на `if platform`.
- Обновления библиотеки ломают API. Митигация: закреплённая версия, обновление — отдельной задачей с проверкой сборки.
- Прототип опережает ратификацию ADR. Митигация: код лежит в `frontend/constructor/`
  как прототип; в `tech-stack.md` стек вносится только после `accepted`.
