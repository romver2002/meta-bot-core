# ADR-0003: Движок сценариев на блоках + изолированные Python-блоки

> Черновик на ратификацию командой. Перенесён из проектного обсуждения;
> `accepted` ставит владелец раздела ([README.md](README.md)).

## Контекст

Конструктор должен быть гибким, но управляемым. Наблюдавшийся у других команд подход —
«блоки для вида, а вся логика в Python-скриптах» — превращает продукт не в no-code
конструктор, а в «неудобную IDE в браузере»: тяжело поддерживать, небезопасно,
непредсказуемо. При этом совсем без кода не покрыть редкую кастомную логику
(расчёт скидки, скоринг, нестандартная валидация).

Ключевая формулировка: конструктор должен генерировать **не код бота, а исполняемый
сценарий**; Python-блоки — подключаемые чистые функции внутри этого сценария.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| 1. Только блоки, без кода | Максимально безопасно и предсказуемо | Не покрыть редкую кастомную логику; упираемся в потолок |
| 2. Всё логикой в Python-скриптах, блоки — обёртка | «Всё можно» | Небезопасно, не отлаживается визуально, не масштабируется, невозможно сопровождать |
| 3. **Блоки — основной язык (80–90%), Python — аварийный выход (10–20%) в песочнице** | Понятно и безопасно для большинства; гибко для сложного | Нужны движок графа, контракт блока и изолированный executor |

## Решение

- Сценарий — это **граф**: `Flow` из узлов (`Node`) и переходов, с входными
  триггерами (`Trigger`). Узел — не картинка, а данные (`send_message`,
  `show_buttons`, `ask`, `condition`, `open_mini_app`, `save`, `http_request`,
  `custom_code`). Движок (`RunFlowUseCase`) исполняет граф; состояние пользователя —
  `Session` (FSM). Термины и инварианты — [../domain/glossary.md](../domain/glossary.md),
  [../domain/domain-model.md](../domain/domain-model.md).
- **Python-блок = чистая функция** `run(context: dict) -> dict`. Он получает вход,
  что-то считает и возвращает результат. Он **не** управляет ботом и не имеет
  прямого доступа к БД, токенам, файловой системе, env и сети.
- Исполнение — через порт `CodeExecutorPort`; реализация в
  `infrastructure/code_executor/` запускает код **в изолированном воркере** с
  ограничениями: таймаут 1–3 c, лимит памяти, запрет ФС/env, сеть — только whitelist,
  лимит размера ответа, версионирование скрипта, логирование ошибок (BR-004,
  [../architecture/security.md](../architecture/security.md)).
- Flow-движок к Python-блоку обращается только через порт — сам пользовательский код
  никогда не исполняется в процессе движка.

## Последствия

**Положительные:**
- Большинство сценариев собирается блоками — понятно, безопасно, отлаживаемо.
- Сложное закрывается Python-блоком без превращения продукта в IDE.
- Изоляция executor'а защищает ядро от зависаний и утечек пользовательского кода.

**Отрицательные:**
- Нужны движок графа, строгий контракт блока и инфраструктура песочницы.
- Граница «что блоками, что кодом» требует поддержки (каталог блоков).

**Риски:**
- Слишком широкий Python-блок = дыра в безопасности и стабильности. Митигация:
  жёсткий контракт `run(context)->dict`, лимиты, изоляция; ревью прав executor'а —
  апрув владельца `architecture/`.
- Если пользователи вынуждены писать Python даже для базовой логики — сигнал, что
  каталог блоков слаб; отслеживаем в [../product/metrics.md](../product/metrics.md).
