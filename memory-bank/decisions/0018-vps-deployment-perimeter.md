# ADR-0018: Развёртывание на VPS — публичный периметр и место внешних потребителей

## Контекст

Владелец: «данный бот должен быть отдельной единицей, так как следует в VPS
выкладывать, и он должен работать». Требование «должен работать» — про
непрерывность: сейчас весь контур живёт на рабочей машине за dev-туннелем
cloudflared, поэтому бот молчит, когда машина спит, а при перезапуске туннеля
меняется URL и подписку на вебхук надо ставить заново (это уже давало инцидент
«/start ничего не делает»).

Что при переезде становится другим — не мощность, а **периметр**. Пока сервис
слушает localhost, отсутствие аутентификации Admin API
([../architecture/security.md](../architecture/security.md), пункт 1 списка
«Чего не хватает до прода») — неудобство контура разработки. На публичном хосте
это дыра: `POST /api/bots` подключает любой токен, `GET /api/bots/{id}/flow`
отдаёт чужой сценарий, `PUT /events-token` и `PUT /notifications/{role}`
перенаправляют доставку. Один открытый порт = полный захват всех ботов
инстанса.

Второе: разложение URL не разделяет **управление** и **рантайм**. Под одним
префиксом `/api` лежат и операции конструктора (закрывать), и то, что обязано
быть доступно снаружи: `POST /api/bots/{id}/miniapp/auth` и
`.../miniapp/result` зовёт браузер mini app (BR-007), `POST /api/bots/{id}/events` —
внешний потребитель (ADR-0017). Поэтому «закрыть `/api`» — не решение,
а поломка mini app.

Третье: радар — **отдельная единица** (свой репозиторий, своя БД, свой бот,
свой жизненный цикл), но не автономная программа. Карточка, кнопки и ответ на
`/start` — это данные Flow внутри ядра; платформенного адаптера и токена MAX у
радара нет намеренно (BR-011, ADR-0017): он знает только `bot_id`, events-токен
и адрес ядра. «Отдельная единица» и «работает без ядра» — разные вещи, и
переезд на VPS не превращает первое во второе.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| 1. Оставить как есть (рабочая машина + dev-туннель) | ничего не платим, ничего не администрируем | бот молчит, когда машина спит; URL туннеля меняется — подписка вебхука протухает; требование «должен работать» не выполняется |
| 2. Радар делается автономным: свой токен MAX, свой адаптер, свой приём вебхука | не зависит от ядра совсем | форк движка: рендер карточек, кнопки, сессии, ретраи, TLS Минцифры дублируются во втором репозитории; конструктор перестаёт быть SSoT сценария; прямо против BR-011 и смысла продукта |
| 3. **Один стек на VPS, две единицы: движок + радар** | бот живёт независимо от рабочей машины; постоянный домен закрывает класс «туннель умер»; `/events` вообще не выходит в интернет — радар ходит в ядро по внутренней docker-сети; каждая единица сохраняет свой образ, БД и цикл выката | нужен администрируемый VPS (обновления, TLS, offsite-бэкапы); публичный периметр приходится задавать allowlist'ом вручную — до IAM это единственная защита Admin API |
| 4. Два хоста: ядро отдельно, радар отдельно | изоляция сбоев и ресурсов | events-токен и трафик доставки уходят в интернет; вдвое больше администрирования ради одного личного бота — преждевременно |

## Решение

Вариант 3. На VPS разворачивается **один compose-стек с двумя продуктовыми
единицами**: движок `meta-bot-core` (api + postgres + redis + pg-backup) и
потребитель `freelance-radar` (app + своя postgres). Радар обращается к ядру по
внутреннему имени сервиса (`http://api:8000`), поэтому пара «events-токен +
`POST /events`» остаётся внутри хоста.

**Публичный периметр задаётся allowlist'ом на reverse-proxy — не «всё, кроме».**
Наружу выставляется ровно:

| Путь | Кто зовёт | Чем аутентифицирован |
|---|---|---|
| `POST /webhooks/{platform}/{bot_id}` | платформа (TG/MAX) | общий `WEBHOOK_SECRET` (пер-ботовый — открытый кандидат в ADR) |
| `POST /api/bots/{bot_id}/miniapp/auth` | браузер mini app | init data платформы, BR-007 |
| `POST /api/bots/{bot_id}/miniapp/result` | браузер mini app | init data платформы, BR-007 |

Всё остальное под `/api` (конструктор, подключение ботов, публикация,
секреты, реестр ролей, events-токен) публично **не маршрутизируется**. До
появления IAM конструктор и Admin API доступны только через SSH-туннель на
`localhost` VPS. `/healthchecks/` — внутренний, для docker и мониторинга.

Граница решения: это решение про **эксплуатацию и периметр**, оно не меняет
слои, порты и доменную модель. Радар остаётся отдельным репозиторием и отдельным
образом; ядро не получает знания о радаре.

Сопутствующее, что решение делает обязательным:

- `WEBHOOK_BASE_URL` = постоянный домен → публикация сама регистрирует вебхук
  (ADR-0014 перестаёт быть no-op, каким он остаётся в dev-контуре).
- Радару нужен свой `Dockerfile` и сервис в compose: сегодня он запускается на
  хосте через `uv`. Планировщик (APScheduler) — ровно **одна** реплика.
- Движок тоже в одной реплике: leader-lock фоновой чистки ПДн не реализован
  (ADR-0011), масштабирование репликами до него запрещено.
- Секреты — файлы `.secrets/`, смонтированные с хоста (прод-vault остаётся
  открытым пунктом); в образ они не запекаются.

**Следующий шаг, который снимает хрупкость периметра** (отдельной задачей, не
блокирует переезд): вынести рантайм-эндпоинты из `/api` под собственный префикс
(например, `/public`), чтобы правило прокси перестало зависеть от совпадения
путей. Текущая раскладка безопасна в правильную сторону — новый эндпоинт под
`/api` по умолчанию окажется закрытым, — но новый *рантайм*-эндпоинт при этом
молча окажется недоступен снаружи.

## Последствия

**Положительные:**

- Бот работает, когда рабочая машина выключена, — исходное требование владельца.
- Постоянный URL вебхука закрывает повторяющийся инцидент «подписка протухла,
  `/start` молчит».
- Доставка радар→ядро не покидает хост: events-токен не ходит по интернету.
- Разделение продуктов, за которое заплачено инцидентом 2026-07-26, переносится
  на прод как есть: две единицы, два образа, две БД, один движок.

**Отрицательные:**

- Появляется администрируемая машина: обновления ОС, TLS-продление, offsite-копии
  БД (сейчас закрыт только локальный `pg_dump` с ротацией).
- Ещё один образ и compose, которые надо держать синхронными с двумя репозиториями.
- Две Postgres на одном небольшом хосте — по памяти считать заранее.

**Риски:**

- **Главный**: неаккуратное правило прокси открывает Admin API наружу — это не
  утечка, а полный захват (чтение и подмена любого сценария, подключение своего
  бота, увод адресатов). Сигнал: любой ответ, кроме отказа, на `GET /api/bots`
  снаружи хоста. Проверять внешним запросом после каждой правки конфигурации
  прокси, а не «по памяти».
- Пересмотр решения — при появлении IAM Admin API: тогда периметр перестаёт
  держаться на allowlist'е, и конструктор можно публиковать нормально.
- Общий `WEBHOOK_SECRET` на все продукты: владелец секрета может подать update
  в любого бота инстанса (`bot_id` берётся из URL и с платформенной личностью
  не сверяется). На одном хосте с двумя своими продуктами это терпимо, при
  первом чужом боте — нет.
