# ADR-0016: Идемпотентное подключение бота по токену

## Контекст

`POST /bots` создавал новую запись `Bot` при каждом вызове: дедупликация была
только по `bot_id`, который API генерирует заново. Каждый повторный connect
того же токена (панель конструктора, smoke-скрипты) добавлял дубль — реестр
«Мои боты» показал три записи одного @MetaFlowAssistantBot, из которых рабочая
одна (вебхук привязан к её URL). Сила против наивного решения: токен — секрет,
живёт только в vault (BR-002, security.md), колонку «токен» для unique-индекса
завести нельзя; перебирать vault на каждый connect — тоже нет (секреты
достаются по ссылке, обратного поиска нет).

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| 1. Оставить как есть | ничего не делать | дубли копятся при каждом connect; «какой из трёх настоящий» — вечный вопрос |
| 2. Unique-индекс по токену открытым текстом | простой дедуп | секрет в БД — прямое нарушение BR-002/security.md |
| 3. Односторонний SHA-256-отпечаток токена в БД + идемпотентный возврат | секрет невосстановим из отпечатка; дедуп O(1) по индексу; гонка закрыта уникальным индексом | +1 колонка и миграция; боты, подключённые до отпечатка, не дедупятся (лечится разовым backfill в dev) |
| 4. Эндпоинт удаления ботов вместо дедупа | чистит следствие | не лечит причину; удаление тянет vault/сессии/вебхук — отдельный больший объём |

## Решение

Вариант 3. Токен нормализуется (strip) ровно один раз на входе use case —
отпечаток и vault получают одно и то же значение (иначе токен с хвостовым
переводом строки залипал бы в vault в нерабочем виде). `Token` получает поле
`fingerprint` (SHA-256 нормализованного токена), хранится в `bot.token_hash`
(TEXT NULL, уникальный индекс `ix_bot_token_hash`; NULL у «доотпечаточных»
ботов индексом не ограничивается — миграция `0002`). `CreateBotUseCase` перед
созданием ищет бота через `BotRepository.find_by_token_fingerprint` и
возвращает существующего — `name`/`platform` запроса при этом игнорируются
(имя правится сохранением сценария, платформа неизменяема). Гонку двух
одновременных connect закрывает уникальный индекс, а идемпотентность
сохраняется и под гонкой: проигравший компенсирует свою запись в vault
(`TokenVaultPort.delete` — сирот-копий секрета не остаётся) и повторным
поиском возвращает победителя. Конструктор при connect бота с непустым
`flow_id` сразу предлагает открыть его сценарий (read-контракт
`GET /bots/{id}/flow`); при отказе row_version черновика всё равно
подхватывается, чтобы «Сохранить» легально перезаписал серверную версию.

Граница: правило действует на подключение (BR-009); удаление ботов из реестра
остаётся отдельным решением (деструктивно: vault, сессии, вебхуки).

## Последствия

**Положительные:**
- «Один токен = один бот»: дубли не появляются, connect для владельца токена
  превращается во «вход в свой сценарий».
- Секрет по-прежнему только в vault; в БД лежит невосстановимый отпечаток.

**Отрицательные:**
- Миграция и +1 колонка; существующие записи требуют разового backfill
  отпечатков (в dev выполнен из `.secrets`, у прода понадобится процедура).

**Риски:**
- Смена токена бота на платформе (revoke) делает старый отпечаток «висячим» —
  connect с новым токеном создаст нового бота; сигнал — жалоба «бот
  подключился, а сценарий пустой»; лечение — будущий `PUT /bots/{id}/token`.
