# ADR-0012: Обновление отправленных сообщений (edit-in-place ответа на нажатие)

## Контекст

Движок отправляет сообщения только append-only: каждый шаг сценария — новое
сообщение в чате. Все прежние меню (`show_buttons`) остаются в истории
кликабельными и «протухают»: их кнопки либо ведут не туда, либо мертвы
(частично закрыто ack'ом `answer_callback`, но само меню висит). Проблема
поднята командой 2026-07-10/11 (обсуждение методов правки/удаления MAX):
чат бота засоряется, старые меню собирают клики.

Обе платформы дают примитивы правки и удаления своих сообщений:
Telegram — `editMessageText`/`deleteMessage` (адресация `chat_id + message_id`),
MAX — `PUT /messages?message_id=` / `DELETE /messages?message_id=` (без
`chat_id`); формы ответов и различия зафиксированы в
[../architecture/platform-reference.md](../architecture/platform-reference.md)
и specs/002-platform-deep-dive. Проверка по официальным докам (2026-07-11,
адверсариальный рой): правка **меню** (сообщения с inline-клавиатурой) на
обеих платформах фактически не ограничена давностью — у MAX это documented
(без клавиатуры — 7 суток в диалогах), у Telegram документированного лимита
на правку ботом своих сообщений нет («48 часов» относится к `deleteMessage`
и business-сообщениям не от бота). Гарантий всё равно нет (у TG старые
сообщения могут выпасть из cloud storage бота) — любой вызов правки/удаления
обязан быть best-effort с фолбэком.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| 1. Оставить как есть (append-only) | ничего не делать | чат засоряется; протухшие меню копятся — источник жалоб и мёртвых кликов |
| 2. Edit-in-place по callback: первый ответ правит сообщение с нажатой кнопкой; отказ → новое сообщение + best-effort удаление старого | стандартный UX ботов (меню «перелистывается» на месте); не требует хранить id в Session/БД — id приходит в самом callback; деградирует в текущее поведение | не чинит меню, «убитое» text-детуром (там нет message_id); меняет видимое поведение опубликованных ботов |
| 3. Трекать id последнего меню в `Session` и обновлять/удалять его при любом событии | чинит и text-детур | новое поле Session + миграция БД + гонки конкурентных обновлений; правка чужого по времени сообщения чаще бьётся о лимиты давности |
| 4. Всегда удалять предыдущее и слать новое | просто | «мигание» чата; 2 вызова вместо 1 (у MAX лимит 30 rps на хост); у TG удаление ограничено 48 ч, у MAX требует права и лимит не задокументирован; при отказе — то же засорение |

## Решение

Вариант 2. Порт `BotPlatformPort` расширен командами `EditMessageCommand` /
`DeleteMessageCommand` и методами `edit_message` / `delete_message`;
`IncomingEvent.message_id` заполняется **только** для callback-событий
(сообщение бота, на котором нажата кнопка) — чужие сообщения движок не правит
и не удаляет по построению. Первый пользовательский ответ цепочки, запущенной
callback'ом, правит сообщение-источник (текст и клавиатура заменяются целиком;
пустые кнопки = снять клавиатуру); при отказе платформы — обычная отправка
нового сообщения + best-effort удаление протухшего меню. Остальные отправки
цепочки, `notify` (другой чат) и события text/start правку не используют.

Идемпотентность: правка в идентичное содержимое — успех (Telegram
«message is not modified» гасится адаптером), иначе фолбэк дублировал бы
сообщение. Платформенные различия (адресация, `attachments: []` против `null`
у MAX, формы ответов) живут только в адаптерах (BR-005).

## Последствия

**Положительные:**
- Меню обновляется на месте — протухшие клавиатуры не копятся; UX как у
  зрелых ботов (BotFather-стиль).
- Схема БД и `Session` не тронуты; фича деградирует в прежнее поведение при
  любом отказе платформы.

**Отрицательные:**
- Поведение опубликованных ботов меняется без опции отключения (v1);
  per-node режим `append` — осознанно отложен до реального запроса.
- Меню, увезённое text-детуром (catch-all TEXT-триггер), по-прежнему не
  обновляется — у текстового события нет `message_id` (см. известную проблему
  в [../current/progress.md](../current/progress.md); лечится вариантом 3,
  если станет критично).

**Риски:**
- Лимиты давности правки различаются между платформами и могут меняться;
  сигнал — рост фолбэков (отправка+удаление вместо правки) в логах адаптеров.
- У MAX `POST /answers` умеет за один вызов и ack, и правку сообщения —
  оптимизация в один запрос возможна внутри адаптера без изменения порта.
