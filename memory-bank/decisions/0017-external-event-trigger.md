# ADR-0017: Внешний триггер external_event и push-доставка

> Ратифицирован владельцем (Роман) 2026-07-26 — командой «Делай» в ответ на
> явное предложение ратифицировать; реализован в тот же день (BR-010).
>
> Контракт **ответа** эндпоинта и жизненный цикл ключа идемпотентности уточнены
> в [ADR-0019](0019-external-event-delivery-contract.md) (2026-07-28): решение
> ниже не меняется, но `{"delivered": bool}` заменён на честный исход.

## Контекст

Все входы в сценарий сегодня реактивны: `TriggerType` = `start` / `text` /
`callback` / `mini_app_result` (`src/domain/flow/value_objects.py`).
`IncomingEvent` рождается в webhook-роутах из платформенного update и — уже
существующий прецедент HTTP-входа — в `SubmitMiniAppResultUseCase`
(`POST /api/bots/{id}/miniapp/result` → `IncomingEvent` вне вебхука, с
решением `external_chat_id == external_user_id` для личного чата). Но оба
входа инициируются действием пользователя; системно-инициированной доставки
нет: в Admin API (`src/presentation/api/admin_routes.py`) нет эндпоинта
«отправь сообщение / запусти сценарий», блок `notify` (ADR-0010) шлёт третьим
лицам, но только изнутри цепочки, уже запущенной пользователем. Настоящий ADR
обобщает прецедент mini app result до универсального входа «система → сценарий».

Потребители, которым нужен вход «система → сценарий»:

1. «Умный помощник по заявкам» — сообщить клиенту о смене статуса заявки из
   CRM (сегодня заявка после `notify` эфемерна, обратного канала нет).
2. `freelance-radar` — внешний сервис-агрегатор фриланс-заказов (отдельный
   репозиторий рядом): присылает владельцу карточки проектов в Telegram и MAX;
   карточка с кнопками должна собираться в конструкторе, а не в радаре.
3. Будущие интеграции: напоминания, вебхуки внешних систем.

Действующие силы: анти-скоуп ([../product/vision.md](../product/vision.md)) —
ядро не «универсальный бот», планировщики и доменная логика внешних систем в
ядро не втягиваются; BR-005 — без платформенного ветвления; BR-008 — сессии
эфемерны; Admin API пока без аутентификации (зафиксированное расхождение в
[../architecture/security.md](../architecture/security.md)) — эндпоинт,
пишущий живым людям, обязан быть закрыт хотя бы секретом.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| 1. Оставить как есть — внешние сервисы держат свои адаптеры TG/MAX | ядро не меняется | дублирование адаптеров, лимитов, edit-in-place, TLS-контекста MAX в каждом потребителе; карточки нельзя собрать в конструкторе; ядро теряет роль SSoT поведения бота |
| 2. Плоский эндпоинт «send message» без сценария (`POST /bots/{id}/messages`) | просто реализовать | текст и кнопки уезжают из `Flow` в вызывающий сервис; обработка нажатий всё равно требует callback-триггеров — логика режется пополам; дублирует блок `notify` |
| 3. Новый `TriggerType.EXTERNAL_EVENT` + `POST /api/bots/{id}/events`: событие входит в движок как обычный `IncomingEvent` | карточка, кнопки, ветвления целиком в `Flow` (конструктор — SSoT); TG+MAX «бесплатно» через существующие адаптеры; переиспользует `ProcessUpdateUseCase`, сессии, идемпотентность | +1 тип триггера во всех перечнях; нужны адресация, идемпотентность и секрет эндпоинта |
| 4. Отдельный сервис-рассыльщик поверх `BotPlatformPort` | не трогает движок | тот же вариант 2 сбоку: сценарий обходится, кнопки мертвы без триггеров |

## Решение

Вариант 3 — событие внешней системы становится полноправным входом в сценарий.

- **Триггер**: `TriggerType.EXTERNAL_EVENT = "external_event"`; конфиг —
  `event` (имя события, матчинг точным равенством, как `pattern` у `text`).
  Добавляется в каталог ([../domain/flow-blocks.md](../domain/flow-blocks.md)),
  в `ENGINE_V1_CAPABILITIES` обеих платформ (платформонезависим: доставка идёт
  обычными `send_message`/`show_buttons` цепочки) и в конструктор.
- **Эндпоинт**: `POST /api/bots/{bot_id}/events`, тело
  `{event: str, to: {role: str} | {chat_id: str}, payload: dict[str, str],
  event_id: str?}`. Адресация по роли — через существующий
  `NotificationTargetResolverPort` (тот же реестр ролей, что у блока `notify`,
  ADR-0010); `chat_id` — явный `external_chat_id`.
- **Идентичность сессии**: резолвер ролей и тело запроса дают только
  `external_chat_id`, а `IncomingEvent` и `Session` требуют
  `external_user_id` (`ProcessUpdateUseCase` ведёт сессию по паре
  (bot, external_user_id)). Решение v1 — как в `SubmitMiniAppResultUseCase`:
  `external_user_id = external_chat_id`, событие адресуется **только личным
  чатам**; ответственность за то, что роль привязана к личному чату, — на
  владельце реестра ролей (фиксируется в BR-010 и в доке эндпоинта).
  Групповые адресаты — вне v1.
- **Payload**: плоский словарь `str → str`; ключи валидируются теми же
  правилами, что имена переменных `save` (`interpolation.py`); значения
  становятся переменными сессии до исполнения цепочки — карточка рисуется
  обычными `{подстановками}`. Лимит размера тела — как у остального Admin API.
- **Идемпотентность**: по паре (`bot_id`, `event_id`) в Redis с TTL — тот же
  механизм, что дедуп вебхуков (ADR-0004); без `event_id` дедупа нет,
  ответственность на вызывающем.
- **Доступ**: bot-scoped секрет в заголовке `X-Events-Token`. Хранилище —
  **отдельный** порт/неймспейс (например, `EventsTokenPort` + свой файл в
  `.secrets/`), а **не** хранилище секретов подключений: то по контракту
  резолвится движком в `{{secret:*}}` блока `http_request`
  (`ProcessUpdateUseCase._resolve_secrets`) — положи туда входной токен, и
  автор сценария выведет его исходящим запросом на свой сервер. Задаётся
  новым эндпоинтом `PUT /api/bots/{id}/events-token` (по образцу
  существующего `PUT /api/bots/{bot_id}/connections/{name}`, но в свой
  неймспейс). Это временная мера до полноценной auth Admin API — при её
  появлении заголовок не ломается, а дополняется.
- **Сессия**: механизма «вытеснения» в кодовой базе нет (повторный `/start`
  исполняется на той же активной сессии; ADR-0008 описывает только
  TTL-expire). v1 честно наследует это поведение: событие исполняется на
  активной сессии пары (или создаёт новую), payload пишется в её переменные,
  `current_node_id` переходит на цепочку события — незавершённый `ask` при
  этом прерывается (см. риски). Поведение фиксируется тестом при реализации;
  ретеншен — по BR-008 без изменений.

**Уточнение после ратификации (2026-07-26, живой прогон).** Решение выше не
меняется, но запись адреса оказалась не такой, как предполагал текст. Написать
пользователю MAX первым по `chat_id` нельзя: `chat_id` уникален для пары
«пользователь ↔ бот» и снаружи неизвестен (404). Поэтому в реестре ролей адрес
push-получателя записывается конвенцией `user:<id>` — глобальным id
пользователя. Отсюда: `external_user_id = external_chat_id` верно **по
значению** (личный чат — один человек), но не по написанию — вебхук отдаёт тот
же id без префикса. Идентичность сессии берётся из адреса со снятым префиксом
(`domain/addressing.py`), иначе push-карточка и нажатие её кнопки расходятся по
разным сессиям, и обещание «нажатия обрабатываются без единой новой строчки»
не выполняется. Конвенция раскрывается только в адаптерах (BR-005): MAX — в
параметр `user_id`, Telegram — снятием префикса.

Граница решения: ядро даёт **вход**, но не расписание — планировщики, опрос
источников, скоринг и прочая доменная логика остаются в вызывающих сервисах
(для радара — в `freelance-radar`). Rate-limits платформ в ядре по-прежнему
не реализованы (известный гэп) — дозирование разгрузки очереди в v1 лежит
на вызывающем.

При реализации зафиксировать бизнес-правило BR-010: внешнее событие
принимается только с корректным bot-scoped секретом из отдельного
хранилища, недоступного `{{secret:*}}`-интерполяции; payload — плоский
словарь, ключи валидны как имена переменных; адресат v1 — только личный
чат (`external_user_id = external_chat_id`).

## Последствия

**Положительные:**
- Карточки радара и CRM-уведомления собираются в конструкторе и работают на
  TG+MAX одним сценарием; внешние сервисы не заводят своих адаптеров.
- Ядро получает стандартный вход «система → сценарий», не нарушая анти-скоуп:
  ни планировщиков, ни чужой доменной логики внутри.
- Нажатия на кнопки карточек обрабатываются существующей маршрутизацией
  callback без единой новой строчки в движке доставки.

**Отрицательные:**
- +1 тип триггера тянет синхронное обновление каталога, конструктора,
  capability-матрицы, валидации публикации и тестов.
- Эндпоинт с правом писать живым людям появляется раньше полноценной auth
  Admin API — секрет в заголовке обязателен с первого дня.

**Риски:**
- Внешняя карточка прерывает незавершённый `ask` активной сессии
  (`current_node_id` уходит на цепочку события); сигнал — жалобы «бот сбил
  вопрос»; пересмотр — очередь отложенных событий до завершения сессии.
- Роль, привязанная к групповому чату, в v1 не поддерживается — допущение
  `user_id = chat_id` верно только для личных чатов; страховка — фиксация
  в BR-010 и в доке эндпоинта, проверка при ратификации реестра ролей.
- Массовая разгрузка очереди вызывающим без серверного rate-limiter может
  упереться в лимиты платформ (TG ~1 msg/s в чат, MAX 30 rps на хост —
  [../architecture/platform-reference.md](../architecture/platform-reference.md));
  сигнал — 429 в `logs/errors.log`; лечение — RateLimiter в адаптерах
  (существующий гэп, отдельная задача).
- `event_id` опционален — потребитель без него получит дубли при своих
  ретраях; фиксируем в документации эндпоинта.
