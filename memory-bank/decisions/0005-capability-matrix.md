# ADR-0005: Матрица возможностей платформ + единые блоки с мапперами

> Черновик на ратификацию командой. `accepted` ставит владелец раздела.

## Контекст

Платформы совпадают не во всём: текст и кнопки есть у обеих, но специфичные кнопки,
платежи, авторизация mini app и лимиты медиа различаются. Нужно, чтобы конструктор
предлагал пользователю только те возможности, которые реально доступны на платформе
его бота, и чтобы это не превращалось в `if platform` внутри блоков.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| 1. Отдельные блоки `Telegram Send Message` / `MAX Send Message` | Явно | Дублирование; пользователь думает про платформу вместо сценария |
| 2. Один блок с `if platform` внутри | Меньше блоков | Ветвление платформы протекает в ядро (нарушает [0002](0002-domain-core-and-adapters.md)) |
| 3. **Единый блок (`Send Message`, `Show Buttons`, `Open Mini App`) + маппер в адаптере + capability matrix** | Пользователь мыслит сценарием; платформенное — в адаптере; недоступное скрыто | Нужно вести матрицу возможностей и мапперы |

## Решение

- Блоки конструктора **единые и платформонезависимые**: `Send Message`,
  `Show Buttons`, `Ask`, `Condition`, `Open Mini App`, `Save`, `HTTP Request`,
  `Custom Code`. Каждый адаптер платформы превращает команду в своё представление
  (Telegram `InlineKeyboardButton`/`WebAppInfo`, кнопка/ссылка MAX и т.п.).
- **Capability matrix** — реестр возможностей платформ (что доступно в Telegram/MAX):
  текст, кнопки, mini app — общие; специфичные кнопки, платежи, авторизация mini app —
  платформенные. Матрица — в `infrastructure/platforms/` (данные) и отражена в
  [../architecture/patterns.md](../architecture/patterns.md).
- Конструктор по платформе(ам) бота **показывает только доступные блоки/опции**, а
  публикация блока, недоступного на платформе, отклоняется (BR-006).
- Специфику, не сводимую к общей модели (платежи), оформляем как platform-specific
  блоки, доступные только для соответствующей платформы, — но и они за портом,
  без `if platform` в ядре.

## Последствия

**Положительные:**
- Пользователь собирает сценарий, а не «бота под платформу».
- Различия платформ обозримы в одном месте (матрица), а не размазаны по коду.
- Новую платформу добавляем строкой в матрицу + маппером.

**Отрицательные:**
- Матрицу и мапперы нужно поддерживать в актуальном состоянии при изменениях API платформ.

**Риски:**
- Матрица устареет за API платформы. Митигация: сверка при обновлении адаптера;
  расхождение фиксируется по [../_meta/lifecycle.md](../_meta/lifecycle.md).
