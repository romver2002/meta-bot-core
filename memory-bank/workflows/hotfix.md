# Процесс: hotfix

Срочное исправление в продакшене meta-bot-core. Протокол сессии — в [../../AGENTS.md](../../AGENTS.md).
Скорость достигается за счёт **минимизации объёма**, а не пропуска шагов.

## 0. Это точно hotfix?

Hotfix — если верно хотя бы одно **и** нет приемлемого обходного пути:

- продакшен недоступен или деградирует для значимой доли пользователей
  (боты Telegram/MAX не отвечают, вебхуки массово падают, сессии не продвигаются);
- портятся или теряются данные (`Session`, `Flow`, привязки `Bot`→токен);
- активно эксплуатируемая уязвимость безопасности (утечка токена бота или
  init-данных mini app, обход валидации init data — BR-007);
- прямые финансовые потери — станет применимо с появлением платежей
  (в MVP платежей ещё нет, см. [../product/roadmap.md](../product/roadmap.md)).

Пороги по умолчанию (уточнить у команды): деградация/простой затрагивает
≥ 20% активных ботов или пользователей хотя бы одной платформы, либо любая
потеря/искажение сессий и сценариев, либо любая утечка секрета.
Не подходит под критерии → обычный процесс [bug-fix.md](bug-fix.md).
Решение «идём hotfix-путём» подтверждает человек — не запускай процесс молча.

## 1. Перед началом прочитай

- [ ] [../ops/runbooks/README.md](../ops/runbooks/README.md) — нет ли готового ранбука
  под этот инцидент (напр. `002-max-integration-down`).
- [ ] [../ops/releases.md](../ops/releases.md) — процесс внепланового релиза и отката.
- [ ] [../ops/environments.md](../ops/environments.md) — что именно задето и где проверять;
  здесь же граница прав агента на prod и `policy_external_api_calls`.
- [ ] [../ops/observability.md](../ops/observability.md) — логи/метрики для диагностики
  и контроля после выката (5xx вебхуков, доставка сообщений по платформам).

## 2. Минимальный безопасный фикс

1. Ветка — от того, что реально в продакшене (тег/релизная ветка), по
   [../architecture/git-workflow.md](../architecture/git-workflow.md);
   имя вида `hotfix/<кратко-симптом>`.
2. Наименьший диф, устраняющий симптом: точечная правка, отключение фичи флагом,
   откат проблемного коммита. **Без попутного рефакторинга**, переименований
   и «раз уж я здесь» — их место в шаге 5.
3. Обязательный регресс-тест на дефект. Пишется за минуты — пиши сразу (юнит на
   инвариант domain или тест адаптера против **фейкового** HTTP-сервера платформ,
   см. [../architecture/testing-strategy.md](../architecture/testing-strategy.md)).
   Если тест реально не написать быстро — задокументированная ручная проверка на
   stage, но тест всё равно обязателен в пост-фактум-фиксе (шаг 5), без него задача
   не закрыта.
4. Прогони существующий набор тестов и `lint-imports`: фикс не должен ломать
   остальное и не должен ронять границы слоёв.

**Спешка не отключает инварианты проекта:** правило зависимостей
(presentation → application → domain), запрет `if platform == …` вне
`infrastructure/platforms/` (BR-005) и изоляция Python-блоков (BR-004) действуют
и в hotfix — `lint-imports` обязан быть зелёным
([../architecture/overview.md](../architecture/overview.md),
[../domain/business-rules.md](../domain/business-rules.md)). Ослабление арх-линтера
закрыто политикой (`policy_bypass_arch_lint: never`,
[../_meta/policy.md](../_meta/policy.md)).

**Секреты и реальные вызовы платформ:** токены ботов и init-данные mini app не
логируй и не клади в диф/тесты в открытом виде — они живут только в token vault
([../architecture/security.md](../architecture/security.md)). Проверка правки
идёт против фейкового HTTP платформ и тестовых ботов; реальные вызовы Bot API
Telegram/MAX (отправка живым ботам, регистрация webhook) закрыты флагом
`policy_external_api_calls: ask` — только по явной просьбе человека
([../ops/environments.md](../ops/environments.md), [../_meta/policy.md](../_meta/policy.md)).

## 3. Подготовь выкат (выкатывает человек)

1. Подготовь внеплановый релиз по [../ops/releases.md](../ops/releases.md):
   изменения, чек-лист выката и готовую команду отката (предыдущая
   версия/флаг) — откат должен быть готов к немедленному запуску.
2. Ускоренное ревью: fast-track одним ревьюером, но **не пропуск ревью** —
   диф маленький, проверяется быстро ([../architecture/git-workflow.md](../architecture/git-workflow.md)).
3. Сообщи человеку: что подготовлено к выкату, чем проверено, как откатить.
   **Выкат и любые команды на prod выполняет человек** — агенту деплой в prod
   запрещён всегда (`policy_prod_commands: never`),
   см. [../ops/environments.md](../ops/environments.md).

## 4. Сразу после выката

- [ ] Контроль по метрикам и логам
  ([../ops/observability.md](../ops/observability.md)): критерий успеха —
  симптом исчез (вебхуки 2xx, боты отвечают, сессии продвигаются), смежные
  метрики по обеим платформам не деградировали.
  Стало хуже → человек откатывает немедленно, без попыток «дочинить на проде».
- [ ] Зафиксируй в [../current/progress.md](../current/progress.md): инцидент,
  временное решение, что осталось сделать полноценно.

## 5. Пост-фактум (обязательно, в течение 1–2 дней)

1. **Полноценное исправление планом**: hotfix был обходом/костылём → заведи
   задачу на корневую причину и веди её по [bug-fix.md](bug-fix.md) (падающий
   тест + фикс) или [refactoring.md](refactoring.md); отрази план в
   [../current/progress.md](../current/progress.md).
2. **Ранбук**: оформи инцидент по
   [../ops/runbooks/incident-template.md](../ops/runbooks/incident-template.md) —
   симптомы, диагностика, что помогло; добавь в реестр
   [../ops/runbooks/README.md](../ops/runbooks/README.md).
3. Влей hotfix-ветку в основную по [../architecture/git-workflow.md](../architecture/git-workflow.md),
   чтобы фикс не потерялся при следующем релизе.
4. Обнови [../current/active-context.md](../current/active-context.md), если
   инцидент поменял приоритеты.

## Definition of Done

- [ ] Критерии hotfix подтверждены человеком до начала.
- [ ] Диф минимален, без попутных изменений; набор тестов и `lint-imports` зелёные;
      секреты не попали в диф/логи.
- [ ] Подготовлено к выкату по ops/releases.md, команда отката была готова;
      выкат выполнил человек ([../ops/environments.md](../ops/environments.md)),
      симптом устранён по метрикам.
- [ ] Ранбук создан/дополнен; задача на полноценное исправление заведена.
- [ ] `current/progress.md` (и при необходимости active-context.md) обновлены;
      `python scripts/validate_memory_bank.py` проходит, если базу правили.

## Пример

Инцидент: после релиза 1.3.0 все боты MAX замолчали — `ProcessUpdateUseCase`
падает 500-й на вебхуке `/webhooks/max/{bot_id}`, потому что `MaxBotAdapter`
не разбирает новое поле callback-события в маппинге update → `IncomingEvent`.
Критерий «деградация для значимой доли пользователей» подтверждён тимлидом,
готового ранбука нет. Ветка `hotfix/max-callback-parse` от тега `v1.3.0`.
Минимальный фикс — guard на отсутствующее поле в
`infrastructure/platforms/max/mapper.py` (правильный слой — платформенная
специфика в адаптере, без `if platform ==` в ядре); регресс-тест на «сыром»
MAX-апдейте написан за 10 минут против фейкового HTTP, реальные токены не
используются. `lint-imports` зелёный. Выкат выполнил тимлид по releases.md,
откат на v1.2.4 наготове; через 15 минут 5xx вебхуков MAX в норме, боты
отвечают. Пост-фактум: задача «полная валидация схемы MAX-апдейтов» заведена,
ранбук «MAX-боты молчат после релиза» добавлен, hotfix влит в main,
progress.md обновлён.
