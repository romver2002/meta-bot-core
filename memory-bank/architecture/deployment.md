# Топология деплоя: как конструктор живёт на сервере

Ответ на вопрос владельца (2026-07-11): «как из конструктора получается бот,
как он отделяется и функционирует; агрегатор или движок?» — и «как корректно
хранить бек/фронт/mini app на сервере». Черновик на ревю владельца.

## Главная модель: мультитенантный движок (агрегатор), бот = данные

Бот — **не отдельная программа**. Бот — это строки в БД (токен в vault +
опубликованная версия сценария `Flow` в JSONB). Движок один на всех и
интерпретирует сценарии по `bot_id`:

```
автор в РЕДАКТОРЕ (браузер)                 конечный пользователь (TG/MAX)
        │ Admin API: PUT /flow, publish              │ нажимает кнопку
        ▼                                            ▼
┌──────────────────────── ОДИН ДВИЖОК (FastAPI, stateless) ───────────────────┐
│  /api/…  Admin API конструктора      /webhooks/{platform}/{bot_id}          │
│                 │                            │                              │
│                 ▼                            ▼                              │
│   PostgreSQL 16: bot / flow /       ProcessUpdateUseCase: по bot_id         │
│   flow_versions / session           достаёт Flow из БД и исполняет          │
│   Redis 7: идемпотентность          └→ BotPlatformPort → Telegram / MAX     │
└──────────────────────────────────────────────────────────────────────────────┘
```

Следствия:
- «Сделать бота» = записать строку в БД; сотый бот не требует сотого сервера.
- Изоляция ботов — **логическая**: свой токен (vault), свой Flow, свои сессии
  (пара `bot_id`+пользователь), свои секреты подключений и адресаты уведомлений.
- Один и тот же Flow ведёт себя одинаково на TG и MAX: различия платформ —
  только в адаптерах (BR-005), несовместимое отклоняется при публикации (BR-006).
- Выделение бота в отдельный инстанс (dedicated) возможно в будущем — это тот же
  движок с БД из одного бота; архитектура не меняется. Сценарий поставки клиенту —
  раздел [«Отдельная поставка клиенту»](#отдельная-поставка-клиенту-self-hosted) ниже.

## Три продукта репозитория и их место на сервере

| Продукт | Каталог | Что это | Как деплоится |
|---|---|---|---|
| Движок + Admin API | `src/` (Python) | исполняет сценарии, принимает вебхуки, API конструктора | Docker-образ, N stateless-реплик за reverse-proxy |
| Редактор конструктора | `frontend/constructor/` (React) | визуальное редактирование Flow | статика (nginx/CDN), ходит в Admin API |
| Mini app runtime | `frontend/miniapp/` (TypeScript + Vite, platform bridge TG/MAX/Browser) | web-приложение внутри бота | статика на HTTPS/CDN (ADR-0006, раздел «Размещение»); origin вносится в `CORS_ALLOWED_ORIGINS` движка |

Держать три части в одном репозитории — корректно (единые версии контрактов,
один CI); смешивать их деплой — нет: у каждой свой артефакт и свой цикл выката.

## Что хранится на сервере

| Хранилище | Содержимое | Примечание |
|---|---|---|
| PostgreSQL 16 | `bot`, `flow`+`flow_versions` (сценарии, immutable-версии), `session` (FSM), `publish_audit` | ПДн сессий — ретеншен BR-008/ADR-0011 |
| Redis 7 | идемпотентность вебхуков (TTL 24 ч, ключи без ПДн) | эфемерно |
| Secret store | токены ботов (`TokenVaultPort`), ключи интеграций, адресаты уведомлений | сейчас dev-файлы `.secrets/`; прод — Vault/KMS (открытый вопрос) |
| Файлы логов | только локальная разработка (`./logs`, ADR-0013) | прод — stdout → агрегатор |

Движок **stateless**: всё состояние в PG/Redis → горизонтальное масштабирование
репликами за балансировщиком. Единственный синглтон — фоновая чистка ПДн
(нужен leader-lock при нескольких репликах — риск зафиксирован в ADR-0011).

## Отдельная поставка клиенту (self-hosted)

Требование владельца (2026-07-12): клиент может попросить реализацию «отдельно» —
код/дистрибутив, который он запускает и сопровождает сам. Быть готовыми сделать
это быстро и профессионально, без компромиссов по архитектуре.

- **Поставка = тот же движок, а не форк.** Поскольку бот — данные (модель выше),
  self-hosted-инстанс — это тот же Docker-образ движка + compose (PostgreSQL 16,
  Redis 7) + БД с единственным ботом клиента. Кодовая база одна; ветвлений
  «облако/у клиента» в коде не появляется — различия только в конфигурации (env)
  и содержимом БД/vault.
- **Состав бандла поставки**: compose-файл (движок + PG + Redis), экспорт Flow
  клиента (definition — сид при первом старте), env-конфиг
  ([../ops/configuration.md](../ops/configuration.md)), собственный секрет-стор
  клиента за `TokenVaultPort` (его токены к нам не попадают), инструкция запуска
  и обновления (HTTPS-домен для вебхуков — на стороне клиента; миграции Alembic
  идут в образе).
- **Gap-лист до готовности** (закрывается при первом реальном запросе; объём
  небольшой именно благодаря CA):
  1. экспорт/импорт бота — выгрузка Flow + настроек и сид-импорт при старте;
  2. версионированный публичный Docker-образ + образцовый compose-бандл в `ops/`;
  3. клиентская инструкция поставки (запуск, обновление образа, бэкап БД).
- **Границы**: что именно передаётся клиенту (только образ или исходный код)
  и на каких условиях (лицензия/договор) — решение владельца продукта, агент
  это не выбирает. Обновления self-hosted-инстанса клиент ставит сам из
  выпускаемых версий.

## Чего не хватает до прода (сводка открытых пунктов)

1. **IAM Admin API** — сейчас без аутентификации, контур строго dev.
2. **Прод-vault секретов** вместо `.secrets/`-файлов.
3. **Постоянный HTTPS-домен** для вебхуков (сейчас dev-туннель); при заданном
   `WEBHOOK_BASE_URL` публикация сама регистрирует вебхук у платформы
   (ADR-0014); сертификат Минцифры для исходящих в MAX уже вшит в образ
   (`ops/certs/` + Dockerfile).
4. **Агрегатор логов/Sentry и метрики** — ADR-0013 закрывает структуру логов,
   доставка в прод-стек — следующий шаг.
5. Leader-lock фоновой чистки при масштабировании >1 реплики.
6. **PITR/WAL-архив и offsite-копии БД** — сейчас закрыт только базовый
   контур: ежедневный `pg_dump` с ротацией (сервис `pg-backup` в compose,
   restore — [../ops/runbooks/backup-restore.md](../ops/runbooks/backup-restore.md)).
