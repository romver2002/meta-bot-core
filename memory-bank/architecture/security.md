# Безопасность

Инженерные требования безопасности meta-bot-core. Базовые запреты для агентов —
в [AGENTS.md](../../AGENTS.md); здесь — как безопасность устроена в коде
и что проверять на ревью. Ключевые темы конструктора: секреты (токены ботов,
init-данные mini app), изоляция пользовательских Python-блоков (BR-004) и
валидация всего платформенного входа на границе (вебхуки, init data — BR-007).

## Секреты

- Секреты (токены ботов — `Token`, init-данные mini app, строки подключения к
  PostgreSQL/Redis, ключи) никогда не попадают в код, конфиги в репозитории и в
  базу знаний — включая примеры, тесты и фикстуры.
- **Токен бота живёт только в token vault** — за портом `TokenVaultPort`
  (`application/ports/`), реализация — в `infrastructure/`. В БоД (PostgreSQL)
  токен в открытом виде не хранится, в логи и метрики не попадает никогда.
  Где секреты живут и как попадают в приложение —
  [../ops/configuration.md](../ops/configuration.md). Конкретное хранилище
  (Vault / SOPS / секреты CI) — уточнить у команды.
- **MAX: токен передаётся в заголовке `Authorization`, не в query-строке** —
  иначе он оседает в логах прокси и access-логах. Это ответственность
  `MaxBotAdapter` (`infrastructure/platforms/max/`), не бизнес-логики.
- Защита от утечки: секрет-сканер (gitleaks / trufflehog) в pre-commit и CI —
  уточнить у команды (какой инструмент и на каком этапе).
- Секрет попал в git — он скомпрометирован независимо от «быстро удалили»:
  немедленная ротация токена (перевыпуск у платформы + замена в vault),
  действия — [../ops/runbooks/README.md](../ops/runbooks/README.md).

## Аутентификация и авторизация

- **Admin API конструктора** (`presentation/api/admin_routes.py`) закрыт
  аутентификацией — механизм (JWT / сессии) уточнить у команды; реализуется как
  middleware в presentation + сервис в infrastructure, не в бизнес-логике.
- **Webhook-роуты** (`presentation/api/webhook_routes.py`) не имеют пользовательской
  аутентификации — доверие к обновлению строится на валидации подписи/источника
  и идемпотентности (см. «Валидация входных данных на границах»), а не на логине.
- Авторизация: право на операцию над ботом/сценарием проверяется как часть
  сценария use case (application: `CreateBotUseCase`, `PublishBotUseCase` и др.),
  а не только фильтром в UI или роутинге. Модель прав (владелец ресурса / RBAC) —
  уточнить у команды.

## Изоляция пользовательского кода (Python-блок)

Ключевое требование безопасности движка — BR-004 (ADR
[0003-flow-engine-blocks-and-sandbox](../decisions/0003-flow-engine-blocks-and-sandbox.md),
контекст CodeExecution в [../domain/bounded-contexts.md](../domain/bounded-contexts.md)).
`CustomCodeBlock` — это **чужой код** внутри нашего процесса-исполнителя, поэтому
он исполняется как чистая функция `run(context) -> dict` в песочнице за портом
`CodeExecutorPort` (реализация — `infrastructure/code_executor/`). Flow-движок
не вызывает пользовательский код напрямую.

Границы песочницы:

- **Таймаут 1–3 c** на исполнение блока; превышение — принудительное завершение
  и доменная ошибка, не зависание воркера.
- **Лимит памяти** на процесс исполнения; превышение — завершение блока.
- **Нет доступа к**: файловой системе (ФС), переменным окружения (env), токенам
  ботов и token vault, БД (PostgreSQL/Redis), внутренним портам приложения.
- **Сеть — только по whitelist** (список разрешённых адресов конфигурируется),
  по умолчанию сеть закрыта.
- **Лимит размера ответа** (`dict`, возвращаемый из `run`) — защита от раздувания
  состояния и памяти.
- **Версионирование** кода блока — чтобы фиксировать, какая версия исполнялась.
- **Отдельный воркер/контейнер-песочница** — исполнение изолировано от процесса
  presentation/application; краш или враждебный блок не роняет конструктор.
- Ошибки исполнения логируются (без утечки секретов и без сырого пользовательского
  ввода в открытом виде).

`context`, передаваемый в блок, не содержит токенов, соединений с БД и хендлов
инфраструктуры — только данные сценария, необходимые блоку.

## Валидация входных данных на границах

- **Всё платформенное и внешнее валидируется на границе presentation до входа в
  application.** Вебхуки (`webhook_routes.py`) разбираются и проверяются в
  presentation/infrastructure и превращаются в `IncomingEvent` — в application
  не попадает непроверенный сырой update. Приём обновлений в production — через
  webhook (ADR [0004-webhook-platform-integration](../decisions/0004-webhook-platform-integration.md)).
- **Init data mini app валидируется на backend** по правилам платформы (подпись
  Telegram / данные MAX Bridge) **до доверия пользователю** — BR-007 (ADR
  [0006-mini-app-as-web-product](../decisions/0006-mini-app-as-web-product.md)).
  Реализация — `infrastructure/platforms/*/mini_app_auth.py` за портом; данные из
  mini app без успешной проверки подписи не считаются достоверными. Точные алгоритмы
  проверки (Telegram: `HMAC_SHA256` с ключом от `bot_token` + `WebAppData`, проверка
  `auth_date`; MAX: `HMAC_SHA256` по отсортированным параметрам с ключом-токеном) —
  [platform-reference.md](platform-reference.md).
- Инварианты домена дополнительно защищаются в domain: сущность (`Bot`, `Flow`,
  `MiniApp`) нельзя создать в невалидном состоянии (напр. HTTPS-URL для `MiniApp` —
  BR-003). Валидация на границе этого не отменяет.
- Пользовательский ввод не конкатенируется в SQL / shell-команды / пути файлов —
  только параметризованные запросы (SQLAlchemy) и allowlist-подход.
- Ошибки наружу — без внутренних деталей (стектрейсы, SQL, пути, значения токенов):
  код ошибки и безопасное сообщение; подробности — в логи.

## Персональные данные (ПДн)

`IncomingEvent` и `Session` содержат идентификаторы пользователя платформы
(`external_user_id`, `external_chat_id`) и текст сообщений — потенциально ПДн.
Заполнить с учётом юрисдикции (152-ФЗ / GDPR) — уточнить у команды:

- какие ПДн обрабатываются и где хранятся (поля, таблицы, сервисы);
- маскирование ПДн (и обязательно токенов) в логах и метриках — согласовать с
  [../ops/observability.md](../ops/observability.md);
- сроки хранения `Session`/истории и процедура удаления по запросу субъекта.

## Чек-лист security-ревью PR

- [ ] В диффе нет секретов (токенов ботов, init data, строк подключения) —
      в т.ч. в тестах, фикстурах и документации.
- [ ] Токен идёт только через `TokenVaultPort`; не логируется, не пишется в БД
      в открытом виде; для MAX — в заголовке `Authorization`, не в query.
- [ ] Изменения в `CustomCodeBlock`/песочнице не ослабляют изоляцию (таймаут,
      память, запрет ФС/env/сети/БД/токенов, лимит ответа) — BR-004.
- [ ] Новый платформенный вход валидируется на границе presentation; init data
      mini app проверяется по подписи до доверия — BR-007; запросы параметризованы.
- [ ] Admin API endpoint'ы закрыты аутентификацией; права проверяются в use case.
- [ ] ПДн и токены не попадают в логи, метрики и тексты ошибок.
- [ ] Новые зависимости проверены на уязвимости — инструмент (pip-audit /
      dependabot) уточнить у команды.
- [ ] Изменения в auth, работе с токенами, песочнице или обработке ПДн — апрув
      владельца architecture/ ([governance](../_meta/governance.md)).
