# Видение продукта meta-bot-core

Зачем продукт существует и для кого. Самый стабильный документ базы: если он
меняется чаще раза в квартал — это сигнал, что видение не сформулировано.
Владение и правила правок — [../_meta/governance.md](../_meta/governance.md)
(агент этот файл сам не редактирует).

meta-bot-core — конструктор **сценариев** чат-ботов и mini app для Telegram и MAX:
движок исполняемых сценариев + платформенные адаптеры. Формула продукта —
`Bot Constructor = Flow Engine + State Machine + Platform Adapters + Mini App
Runtime`. Это не «универсальный бот» и не «генератор кода бота»: конструктор —
«мозг» **уже зарегистрированного** платформенного бота, он управляет его
поведением по токену, но не создаёт платформенный аккаунт.

## Проблема

У команды уже есть (или скоро будет) зарегистрированный бот — в Telegram и/или
в MAX (в MAX регистрация бота доступна партнёрам). Чтобы бот что-то делал, его
поведение приходится программировать вручную и заново под каждую платформу: SDK,
формат update, модель кнопок и запуск mini app у Telegram и MAX различаются.

В результате бизнес-логика сценария ветвится по платформе (`if platform == …`),
mini app дублируется, а выход на вторую платформу или добавление третьей (VK,
WhatsApp) означает переписывание, а не переиспользование. Стоимость поддержки
растёт с числом платформ, продукт привязан к одному мессенджеру, а типовые
сценарии (`/start`, меню на кнопках, «спросить-ответить», открыть mini app)
собираются каждый раз с нуля.

## Для кого (сегменты пользователей)

| Сегмент | Кто это | Ключевая потребность |
|---|---|---|
| Владелец бота / продакт | у него есть зарегистрированный бот (в т.ч. в MAX для партнёров), знает нужный сценарий, но не хочет писать код под каждую платформу | собрать поведение бота и mini app визуально, блоками, и подключить по токену |
| Разработчик / интегратор | собирает бота на конструкторе, дописывает нестандартную логику | закрыть 80–90 % блоками и добавить оставшиеся 10–20 % Python-блоком, не завязываясь на конкретный мессенджер |
| Команда, выходящая на вторую платформу | уже работает в одном мессенджере, запускается во втором (напр. Telegram → MAX) | переиспользовать один сценарий на новой платформе без переписывания |

> Сегментов должно быть 1–3. Если больше — продукт размывается; лишнее
> перенесите в «Анти-скоуп» или в [roadmap.md](roadmap.md).

## Ценность

Что пользователь получает такого, ради чего откажется от текущего способа.

- **Вместо отдельной реализации под каждую платформу — один сценарий (`Flow`) на
  много платформ.** Ядро оперирует абстракциями (`IncomingEvent`, `Button`,
  `Node`, `Session`), различия Telegram/MAX скрыты за `BotPlatformPort` и
  `CapabilityMatrix` — добавить платформу можно как плагин-адаптер, не трогая
  сценарий.
- **Вместо программирования с нуля — сборка блоками (80–90 %) плюс Python-блок
  для сложного (10–20 %).** Типовые шаги (`send_message`, `show_buttons`, `ask`,
  `condition`, `open_mini_app`) — готовые узлы; нестандартное закрывает
  `CustomCodeBlock` (`run(context) -> dict`) в изолированной песочнице.
- **Вместо привязки к мессенджеру — независимое от платформы ядро.** Конструктор
  «включается» в уже зарегистрированного бота по токену; сменить или добавить
  платформу можно без переписывания бизнес-логики.

## Что продуктом НЕ является (анти-скоуп)

Явные границы. Сюда попадает всё, что регулярно просят, но что мы осознанно
не делаем. Ссылайтесь на этот раздел при отклонении фич.

- **Не регистрирует платформенного бота и не заменяет Telegram/MAX** — аккаунт,
  модерация и лимиты платформы (в MAX: модерация; лимиты 5 ботов для
  организации/ИП, 2 для самозанятого) остаются на стороне платформы; работаем
  с уже выданным токеном (BR-002,
  [../domain/business-rules.md](../domain/business-rules.md)).
- **Не «универсальный бот» и не «генератор кода бота»** — это движок исполняемых
  сценариев + адаптеры; конструктор не выдаёт готовый исходник бота, а исполняет
  `Flow` через ядро.
- **Не среда исполнения произвольного кода** — Python-блок ограничен изолированной
  песочницей (таймаут, лимит памяти, без доступа к БД, токенам, ФС, env; сеть
  только по whitelist), BR-004.
- **Не строит платёжный слой «бесшовно поверх платформ»** — платёжные различия
  Telegram/MAX существенны; платежи вынесены за MVP в [roadmap.md](roadmap.md).

## Ключевые сценарии использования

Топ-сценарии, ради которых продукт существует. Не полный список фич —
только то, что определяет продукт. Детальные правила сценариев —
в [../domain/business-rules.md](../domain/business-rules.md).

| Сценарий | Пользователь | Ценность |
|---|---|---|
| Собрать сценарий бота из блоков: триггер (`/start`, текст, callback), сообщения, кнопки, ветвление, ссылка на mini app | владелец бота / продакт | рабочий бот без кода и без привязки к конкретной платформе |
| Подключить один и тот же `Flow` к боту в Telegram и в MAX по токену и опубликовать | команда, выходящая на вторую платформу | одна логика — две платформы, без переписывания |
| Дописать нестандартный шаг Python-блоком `run(context) -> dict` в песочнице | разработчик / интегратор | сложное закрывается кодом, не ломая изоляцию и границы слоёв |
| Открыть mini app из кнопки с валидацией init data на backend и вернуть результат в сценарий | владелец бота / разработчик | безопасный запуск web-части бота, единый на всех платформах |
