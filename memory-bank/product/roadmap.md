# Roadmap meta-bot-core

**Здесь направления, не задачи.** Задачи живут в беклоге (трекере); этот файл
сверяется с ним при плановом обслуживании (см.
[../_meta/lifecycle.md](../_meta/lifecycle.md)), но не дублирует его.
Агенту roadmap нужен, чтобы понимать, куда движется продукт, и не предлагать
решения против течения. Правки — только по решению владельца продукта
([../_meta/governance.md](../_meta/governance.md)).

Беклог задач ведётся в трекере репозитория meta-bot-core (конкретный инстру-
мент — GitHub Projects / YouTrack — уточнить у команды). Последняя сверка
направлений с беклогом: 2026-07-06.

## Горизонты

Текущий фокус — только в [current/active-context.md](../current/active-context.md).

### Квартал (2–4 направления)

Что начнём после текущего фокуса. Порядок в списке = приоритет.

- **MVP-конструктор end-to-end.** Сквозной путь: Admin UI (создать `Bot`, выбрать
  `Platform` Telegram/MAX, добавить `Token`, собрать простой `Flow` с кнопками и
  ссылкой на mini app) → Webhook Gateway (`/webhooks/telegram/{bot_id}`,
  `/webhooks/max/{bot_id}` → `IncomingEvent`) → Flow Engine (`/start`, текст,
  callback, состояние `Session`) → Message Dispatcher (`SendMessageUseCase` +
  `TelegramBotAdapter`/`MaxBotAdapter`) → Mini App (детект платформы, валидация
  init data, возврат результата в backend). Зачем сейчас: пока формула
  Flow Engine + State Machine + Platform Adapters + Mini App Runtime не прошла
  сквозь один живой сценарий — продукта нет. Приём обновлений — через webhook
  ([../decisions/0004-webhook-platform-integration.md](../decisions/0004-webhook-platform-integration.md)).
  MAX-адаптер писать сразу под `platform-api2.max.ru` (см. срок в «Приоритетах»).
- **Полная capability matrix.** Расширить `CapabilityMatrix` за MVP-минимум,
  чтобы конструктор не предлагал недоступный на платформе блок и отклонял его при
  публикации `Flow` (BR-006). Различия платформ остаются за `BotPlatformPort`, без
  ветвления по платформе в бизнес-логике (BR-005).
  ADR [0005-capability-matrix](../decisions/0005-capability-matrix.md).
- **Python-блоки в песочнице.** `CustomCodeBlock` как чистая функция
  `run(context) -> dict` через `CodeExecutorPort` и изолированный executor:
  таймаут 1–3 c, лимит памяти, без ФС/токенов/БД/env, сеть только по whitelist
  (BR-004). ADR [0003-flow-engine-blocks-and-sandbox](../decisions/0003-flow-engine-blocks-and-sandbox.md)
  (proposed — двигаем после стабильного ядра исполнения).

### Год (крупными мазками)

Направления без обязательств по срокам. Проверяются на соответствие
[vision.md](vision.md): всё, что не работает на видение, сюда не попадает.

- **Платежи в сценарии.** С осторожностью: механики Telegram и MAX различаются;
  поведение прячется за `BotPlatformPort` и описывается в `CapabilityMatrix`,
  никакого `if platform ==` вне `infrastructure/platforms/` (BR-005). Объём и
  модель платежей — уточнить у команды после полной capability matrix.
- **Новые платформы как плагины.** VK / WhatsApp / Avito / сайт-чат подключаются
  как адаптеры через `PlatformFactory` за `BotPlatformPort`, ядро конструктора не
  меняется (ADR [0002-domain-core-and-adapters](../decisions/0002-domain-core-and-adapters.md)).
  Берёмся только на устоявшемся порту, проверенном на Telegram+MAX.

## Приоритеты и обоснование

Почему порядок именно такой — чтобы не переспоривать одно и то же.

| Приоритет | Обоснование |
|---|---|
| MVP-конструктор end-to-end | Первый приоритет по КАНОНУ: без сквозного прохода «создать бота → принять webhook → отработать сценарий → ответить → открыть mini app» продукта не существует. Метрики успеха — [metrics.md](metrics.md). |
| Миграция MAX на `platform-api2.max.ru` | **Жёсткий внешний срок: до 2026-07-19** перевести запросы `MaxBotAdapter` с `platform-api.max.ru` на `platform-api2.max.ru`, токен передавать в заголовке `Authorization` (не в query). Это ops-обязательство, а не бизнес-правило; пропуск срока = отказ MAX-ботов. Поэтому MAX-адаптер MVP пишем сразу под новый endpoint. |
| Полная capability matrix | Снимает риск предложить в конструкторе блок, который платформа не исполнит; включает корректную блокировку при публикации (BR-006). Идёт сразу за MVP, где матрица — минимальная. |
| Python-блоки в песочнице | Даёт расширяемость сценариев без правки ядра, но требует зрелого изолированного executor'а (BR-004); безопасность важнее скорости, поэтому после стабильного Flow Engine. |

## Осознанно отложено

Не «отказались навсегда» (это [vision.md](vision.md), анти-скоуп),
а «не сейчас». Фиксируем причину и условие возврата — иначе тема будет
всплывать каждый спринт.

| Что | Почему отложено | Условие возврата |
|---|---|---|
| Платежи в сценарии | Платформенные различия Telegram/MAX требуют аккуратной модели в `CapabilityMatrix`; ядру ценнее сперва стабильный сквозной сценарий | После MVP и полной capability matrix либо явный спрос клиентов |
| Новые платформы (VK/WhatsApp/Avito/сайт-чат) | Ранняя мультиплатформенность заморозит незрелый `BotPlatformPort`; расширение оправдано только на устоявшихся абстракциях | Стабильный `BotPlatformPort`/`PlatformFactory` на Telegram+MAX и спрос на конкретную платформу |
| Регистрация платформенного бота за пользователя | Вне продукта: аккаунт, модерация и лимиты платформы (MAX: модерация; 5 ботов для организации/ИП, 2 для самозанятого) — на стороне платформы, конструктор работает по готовому токену (BR-002) | Не планируется; пересмотр только при смене видения ([vision.md](vision.md)) |
