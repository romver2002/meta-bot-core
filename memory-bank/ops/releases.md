# Релизы meta-bot-core

Как изменения попадают в prod и как их откатить. Ветки и правила коммитов —
[../architecture/git-workflow.md](../architecture/git-workflow.md);
окружения — [environments.md](environments.md). Срочные фиксы идут мимо
этого процесса — по [../workflows/hotfix.md](../workflows/hotfix.md).

Модель — **trunk-based**: `main` всегда релизопригоден, релиз собирается из `main`,
долгих release-веток нет (см. [../architecture/git-workflow.md](../architecture/git-workflow.md)).

## Версионирование

- Схема: **SemVer** `MAJOR.MINOR.PATCH`. Публичный контракт meta-bot-core, по
  которому считается совместимость: admin API конструктора и webhook-роуты
  (`/webhooks/telegram/{bot_id}`, `/webhooks/max/{bot_id}`) в presentation, а также
  формат хранения сценария (`Flow`/`Node`/`Trigger`/`Button`).
  - **MAJOR** — несовместимое изменение этого контракта (ломающая правка admin API,
    webhook-роутов или схемы `Flow`, требующая изменений у потребителей/данных).
  - **MINOR** — обратно-совместимая функциональность: новый тип `Node`, новый
    адаптер платформы (`TelegramBotAdapter`/`MaxBotAdapter`), расширение
    `CapabilityMatrix`.
  - **PATCH** — фиксы без изменения контракта.
- Версия фиксируется git-тегом `vX.Y.Z` — источник истины; тег ставит CI при
  релизе. Дублирование версии в файле проекта (`pyproject.toml`) — уточнить у команды.
- Changelog: генерируется из Conventional Commits (формат коммитов —
  [../architecture/git-workflow.md](../architecture/git-workflow.md)) в описание
  GitHub Release. Нужен ли отдельный `CHANGELOG.md` — уточнить у команды.

## Процесс релиза по шагам

1. Убедиться, что в `main` всё, что входит в релиз, и CI зелёный: `ruff`
   (format+lint), `mypy` (strict), тесты ([testing-strategy.md](../architecture/testing-strategy.md)),
   валидатор базы знаний и арх-линтер `lint-imports` в джобе `arch-lint`
   ([../../.github/workflows/arch-lint.yml](../../.github/workflows/arch-lint.yml)) —
   протечка слоёв закрывает мерж и релиз.
2. Пройти чек-лист перед релизом (ниже).
3. Создать релиз: поставить тег `vX.Y.Z` на релизном коммите `main` — CI собирает
   артефакт и публикует GitHub Release.
4. Деплой на **stage**: через CI/CD; прогнать смоук основного пути MVP — создать
   бота (Telegram и MAX), простой сценарий (`/start` → кнопка → mini app), проверить
   приём webhook и отправку сообщения.
5. Получить подтверждение выхода на prod: кто аппрувит — уточнить у команды
   (разумный дефолт — тимлид или релиз-дежурный).
6. Деплой на **prod**: через CI/CD, ручным триггером после аппрува (авто-деплой
   в prod не используется).
7. Пост-проверка prod (15–30 минут): смоук-сценарий, дашборды и алерты —
   [observability.md](observability.md).
8. Объявить о релизе: канал/формат — уточнить у команды.

Агент шаги 3–7 сам не выполняет: деплой и любые prod-команды закрыты политикой
(`policy_prod_commands: never`, [../_meta/policy.md](../_meta/policy.md)) и правилами
окружений ([environments.md](environments.md)). Агент готовит изменения, тег и
чек-лист — запуск за человеком.

## Чек-лист перед релизом

- [ ] CI зелёный на релизном коммите; тесты не скипнуты; `lint-imports` зелёный
  (границы слоёв не протекли).
- [ ] Миграции БД: их создание и применение — только по явной просьбе человека
  (`policy_db_migrations: ask`, [../_meta/policy.md](../_meta/policy.md)); миграции
  обратимы или есть явный план отката данных.
- [ ] Новые переменные окружения заведены во всех окружениях
  ([configuration.md](configuration.md)).
- [ ] Breaking changes admin API / webhook-контракта / формата `Flow` согласованы
  с потребителями (mini app, внешние интеграции) — с кем именно, уточнить у команды.
- [ ] **Релиз затрагивает интеграцию с MAX** → выполнены требования из блока
  «Особое: релизы, затрагивающие MAX» (ниже).
- [ ] Версия (тег) и changelog обновлены.
- [ ] Известно, какой релиз сейчас в prod (точка отката).

## Особое: релизы, затрагивающие MAX

Любой релиз, меняющий интеграцию с MAX, обязан использовать хост
**`platform-api2.max.ru`** (не `platform-api.max.ru`), а токен бота передавать в
заголовке `Authorization`, не в query. Это техническое требование платформы с
жёстким дедлайном миграции — **до 2026-07-19**; пропуск ломает интеграцию с MAX.
Детали и первоисточник — [ADR-0004](../decisions/0004-webhook-platform-integration.md)
и [../architecture/platform-reference.md](../architecture/platform-reference.md);
конфигурация хостов/секретов — [configuration.md](configuration.md). Токены — только
в token vault, в логи и changelog не попадают.

## Откат

1. Решение об откате принимает релиз-дежурный или тимлид (роль уточнить у команды).
   Критерий: ошибки на ключевом сценарии (приём webhook, исполнение `Flow`,
   отправка сообщения), когда forward-fix дольше ~30 минут.
2. Откатить приложение на предыдущую версию: redeploy предыдущего тега `vX.Y.Z`
   через CI/CD (точная команда/кнопка — уточнить у команды). Прямых prod-команд
   агент не выполняет — готовит инструкцию для человека.
3. Миграции: создание/применение — по `policy_db_migrations: ask`. Если релиз менял
   схему БД — действовать по плану отката из чек-листа; **не** откатывать схему
   вслепую, forward-fix предпочтительнее реверса миграции.
4. Убедиться по метрикам, что симптом ушёл ([observability.md](observability.md)).
5. Завести инцидент и ранбук — [runbooks/README.md](runbooks/README.md)
   (шаблон — [runbooks/incident-template.md](runbooks/incident-template.md)).

## Вопросы заполняющему

- Возможен ли частичный выкат (canary, фиче-флаги)? Если да — опиши, когда применять.
- Кто аппрувит выход на prod и в каком канале объявляется релиз? Уточнить у команды и зафиксировать.
