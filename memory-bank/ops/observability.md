# Наблюдаемость meta-bot-core

Где смотреть логи, метрики, трейсы и алерты, и как мы логируем.
Первый адрес при инциденте — сюда, затем [runbooks/README.md](runbooks/README.md).

Смысл продуктовых метрик (что считаем успехом) — в [../product/metrics.md](../product/metrics.md);
здесь — техническая наблюдаемость сервиса. Что за чем стоит по слоям — см.
[../architecture/overview.md](../architecture/overview.md).

## Куда смотреть

Конкретный стек наблюдаемости (Prometheus + Grafana для метрик, Grafana Loki
или Sentry для логов/ошибок) — **уточнить у команды**; ниже — какой сигнал где
искать. Ссылки должны вести на сохранённый поиск/дашборд, а не на главную
страницу инструмента.

| Сигнал | Инструмент | Ссылка / где искать |
|---|---|---|
| Логи приложения | Grafana Loki / ELK — уточнить у команды | Сохранённый поиск по `app="meta-bot-core"` и `env` — уточнить у команды |
| Метрики (RPS, латентность, ошибки) | Prometheus + Grafana — уточнить у команды | Основной дашборд сервиса — уточнить у команды |
| Трейсы | OpenTelemetry → Tempo/Jaeger — на MVP не собираем (уточнить у команды) | — |
| Алерты | Alertmanager → канал команды — уточнить у команды | Реестр правил и канал `#meta-bot-core-alerts` — уточнить у команды |
| Ошибки (exception tracking) | Sentry или аналог — уточнить у команды | Проект `meta-bot-core` — уточнить у команды |

Уровень логов и адреса бэкендов наблюдаемости задаются конфигурацией по окружению —
см. [configuration.md](configuration.md) и [environments.md](environments.md).

Пример поиска (адаптируйте под свой стек логов): в Grafana Loki
`{app="meta-bot-core", env="prod"} |= "webhook" |= "ERROR"` — упавшие обработки
вебхуков в prod; для конкретного бота добавьте фильтр по `bot_id`.

### Ключевые точки наблюдения meta-bot-core

За чем смотрим в первую очередь (компоненты и use cases — из
[../architecture/overview.md](../architecture/overview.md)):

- **Обработка вебхуков** — роуты `presentation/api/webhook_routes.py`
  (`/webhooks/telegram/{bot_id}`, `/webhooks/max/{bot_id}`) и `ProcessUpdateUseCase`.
  Логируем и метрим: приём update, результат (успех/ошибка), код ответа роутера,
  **сработала ли идемпотентность** — отброшен ли повторный update по ключу в Redis
  (дубликаты вебхуков — норма). Приём в prod только через webhook — ADR
  [0004-webhook-platform-integration](../decisions/0004-webhook-platform-integration.md).
- **Исполнение сценариев** — `ProcessUpdateUseCase` (цепочка узлов — `_run_chain`).
  Реализовано: три WARN в `ProcessUpdateUseCase` (неподтверждённое нажатие кнопки,
  непривязанная роль уведомления, недоставленное уведомление) плюс логирование
  приёма/исхода вебхука (ADR-0013). Вход в узел (`Node`), переход состояния
  (`Session`), исход шага — **план**. Метрики: длительность прохода сценария,
  доля упавших шагов по типу узла (тоже план).
- **Ошибки Python-блоков** — исполнение `CustomCodeBlock` через `CodeExecutorPort`
  в песочнице. Отдельно считаем: таймаут (1–3 c), превышение лимита памяти,
  исключение внутри `run(context)`, превышение лимита размера ответа. Правило и
  ограничения — BR-004 ([../domain/business-rules.md](../domain/business-rules.md)),
  ADR [0003-flow-engine-blocks-and-sandbox](../decisions/0003-flow-engine-blocks-and-sandbox.md).
  Наружу пишем факт и код ошибки, **без** содержимого контекста, способного нести
  секреты.
- **Задержки Bot API** — каждое обращение к Telegram/MAX через `BotPlatformPort`
  (`TelegramBotAdapter` / `MaxBotAdapter`): платформа, метод, длительность, статус,
  ретраи. **Не реализовано — план**: адаптеры сейчас вызовы не логируют, а логгеры
  `httpx`/`httpcore` намеренно подняты до WARNING — httpx на INFO пишет полный URL
  запроса, у Telegram в URL токен (`infrastructure/observability/logging_setup.py`).
  Медленный или деградировавший Bot API виден здесь раньше, чем в жалобах.
  Платформенные ограничения (порты webhook Telegram, хост MAX
  `platform-api2.max.ru`, токен в `Authorization`) — [../architecture/platform-reference.md](../architecture/platform-reference.md).

## Соглашения о логировании

### Уровни

- **ERROR** — операция не выполнена, нужно действие человека или это кандидат в алерт
  (упавшая обработка вебхука, необработанное исключение в `ProcessUpdateUseCase`).
- **WARN** — деградация или подозрительное состояние; операция выполнена
  (ретрай Bot API, отброшенный дубль вебхука, приближение к таймауту песочницы).
- **INFO** — значимые бизнес-события и переходы: принят `IncomingEvent`, переход
  `Session`, публикация бота, отправка сообщения.
- **DEBUG** — диагностика для разработки; в prod выключен
  (уровень задаётся переменной — см. [configuration.md](configuration.md)).

### Логируем обязательно

- Все необработанные исключения — со стек-трейсом, на ERROR.
- Приём и исход каждого вебхука: платформа, `bot_id`, `event_type`, результат,
  признак идемпотентности (обработан/дубль отброшен).
- Вызовы Bot API Telegram/MAX через `BotPlatformPort`: платформа, метод,
  длительность, статус (без тел запросов и без токена) — **не реализовано, план**:
  адаптеры не логируют, `httpx`/`httpcore` подняты до WARNING (токен в URL Telegram).
- Ошибки исполнения сценария (`ProcessUpdateUseCase`) и ошибки
  песочницы (`CodeExecutorPort`): тип и код ошибки, без содержимого контекста блока.
- Идентификатор корреляции в каждой записи запроса: `request_id` на границе HTTP,
  сквозная связка вебхука с исполнением через ключ идемпотентности (Redis) и
  `bot_id`; проброс — `ContextVar` в `application/observability.py`, ставит
  HTTP-мидлварь, читает JSON-форматтер (ADR-0013); ответ несёт `X-Request-ID`.
- Структурно: одна JSON-строка на запись (stdlib `logging` + свой форматтер,
  решение [ADR-0013](../decisions/0013-structured-logging.md)); всегда stdout,
  локально дополнительно файлы `logs/app.log` и `logs/errors.log` (ERROR+).

**Чужая настройка логирования не глушит наши логгеры.** `logging.config.fileConfig`
по умолчанию отключает все уже созданные логгеры, которых нет в его конфиге, —
поэтому Alembic (`migrations/env.py`) вызывает его с `disable_existing_loggers=False`.
Иначе прогон миграций в одном процессе с приложением (фикстура интеграционных
тестов, разовый апгрейд из кода) молча выключал бы всё `app.*` до конца процесса:
приложение работает, а в логе пусто. Симптом в тестах — `caplog` перестаёт видеть
записи в тестах, идущих после интеграционных.

### Логировать запрещено

- Секреты: **токены ботов (`Token`) и init-данные mini app — не логировать никогда**,
  как и содержимое заголовка `Authorization` (в MAX токен идёт именно в нём),
  cookie, строки подключения к PostgreSQL/Redis. Политика и способы хранения —
  [../architecture/security.md](../architecture/security.md).
- Полный сырой update (`raw`) и тела запросов/ответов на INFO и выше: могут нести
  ПДн и текст пользователя. `text`/`payload` — только на DEBUG и по необходимости.
- ПДн пользователя платформы: имя, username, телефон, адрес, платёжные данные —
  в открытом виде никогда. `external_user_id`/`external_chat_id` пишем как
  идентификаторы платформы (для корреляции), а не как персональные данные;
  при сомнении — маскирование.

## Алерты

- Правило: алерт либо требует действия, либо его не должно существовать
  (шумные алерты чиним или удаляем).
- На каждый повторяющийся алерт — ранбук: [runbooks/README.md](runbooks/README.md).
- Базовый набор (пороги — уточнить у команды, ниже разумные дефолты):
  - доступность healthcheck сервиса (алерт при недоступности > 1–2 мин);
  - error rate обработки вебхуков (`webhook_routes` + `ProcessUpdateUseCase`),
    например > 2% за 5 мин;
  - доля упавших проходов сценария (`ProcessUpdateUseCase`);
  - сбои песочницы (`CodeExecutorPort`): всплеск таймаутов/OOM — сигнал о плохом
    блоке или нехватке ресурсов воркера;
  - латентность Bot API p99 по платформам (`TelegramBotAdapter`/`MaxBotAdapter`) —
    нереализуемо, пока не появится логирование/метрики вызовов Bot API
    (см. «Задержки Bot API» выше — план);
  - ресурсы инфраструктуры: PostgreSQL 16 и Redis 7 (соединения, память, задержки).

## Вопросы заполняющему

- Сможет ли новый человек по таблице выше за 5 минут найти логи конкретного
  вебхука в prod по `bot_id`? Если нет — добавь прямую ссылку на сохранённый поиск.
- Что сработает первым при падении prod — алерт или жалоба пользователя?
- Точно ли ни токен, ни init-данные mini app не утекают в логи на пути
  webhook → `ProcessUpdateUseCase` → адаптер платформы?
